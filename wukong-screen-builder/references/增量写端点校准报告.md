## 二、逐端点对照分析

### 1. WK.write.newPage — 新建页面

- **URL**: `POST unity/page/`
- **当前 wukong-client.js 假设的 body**:
  ```js
  meta = {name, width, height, groupId, type:'PAGE', kind:'PAGE', ...}
  // 直接把 meta 对象作为 body POST
  ```
- **内部资料/导出包中的真实字段** (`导出包结构与写契约.md` §4 page 实体，43 键):
  ```
  必须字段（推断）:
    id                    - uuid（应由后端生成，但导出包中含，导入时会覆盖）
    name                  - 页面名称
    type                  - "PROJECT" / "PAGE" / "POPUP" / "TEMPLATE"
    kind                  - "PAGE" | "POPUP"
    width                 - 画布宽度(px)，如 1920
    height                - 画布高度(px)，如 1080
    groupId               - 所属分组 UUID
    project               - 所属项目 UUID（导出包中必有）
  可选字段:
    previewMode           - "ORIGINAL" | "STATIC"
    templateStyleType     - 如 "专题模板"
    styleConfigId         - 皮肤外键 UUID
    mapConfigId           - 地图配置外键
    linesConfigId         - 辅助线外键
    imageUrl              - 封面图 URL
    style                 - array（10 项页面级属性面板配置）
    lines                 - {v:[], h:[]}（辅助线像素坐标）
  ```
- **差异分析**:
  | 字段 | 当前假设 | 导出包/读返回 | 差异 |
  |------|---------|-------------|------|
  | `project` | 缺失 | 页面实体必含 `project` 字段(所属项目 id) | **可能必填** |
  | `type` | 'PAGE' | 导出包值为 "PROJECT"/"PAGE"/"POPUP"/"TEMPLATE" 等 | 需确认新建页面是否用 "PAGE" 还是 "PROJECT" |
  | `id` | 缺失(靠后端生成) | 合理，但需确认后端是否要求客户端传 uuid | 未知 |
  | `previewMode` | 缺失 | 默认可能不需要 | 低风险 |
  | `style` | 缺失 | 读返回有 12 项 style 数组；新建时后端可能用默认 | 可选 |
- **置信度**: **中** — `project` 字段是否必填是关键未知项；`type` 的枚举值选择需确认
- **需要抓包确认**: 是。手工新建一个空白页面，抓 `POST unity/page/` 的真实 body

### 3. WK.write.addCard — 新增单个组件

- **URL**: `POST unity/page-card`
- **当前 wukong-client.js 假设的 body**:
  ```js
  card = 单个 pageCard（base.code + x/y/width/height + style + data）
  // 注释说"单个 pageCard"但未明确必填字段列表
  ```
- **findings/09-pagecard.md §6 最小骨架字段**:
  ```json
  {
    "id": "<新生成 uuid>",
    "pageId": "<目标页面 id>",
    "cardId": "<组件定义 id>",
    "name": "<实例显示名>",
    "x": 0, "y": 0,
    "width": 200, "height": 150,
    "level": 10,
    "beGroup": false,
    "beHidden": null,
    "beLocked": null,
    "parentId": null,
    "disabled": false,
    "styleConfigId": "<clone 自 base.styleConfigId>",
    "dataId": "<clone 自 base.dataConfigId>",
    "style": { "base": {}, "configuration": [] },
    "data": {},
    "interaction": null,
    "children": [],
    "cardChildren": null,
    "cardDataChildren": null,
    "grade": 1,
    "totalGrade": 1
  }
  ```
- **差异分析**:
  | 字段 | 当前假设 | 真实结构(推断) | 差异 |
  |------|---------|--------------|------|
  | `id` | 未提及 | **必填**，客户端生成 uuid | 新增字段 |
  | `pageId` | 未传(land 里手动加) | **必填** | 需在方法签名里体现 |
  | `cardId` | 隐含在 base.code 里 | **必填**，应传组件定义 ID 而非 base.code | **关键差异** |
  | `styleConfigId` | 未提及 | 需传实例样式 ID(clone 自 base) | 新增字段 |
  | `dataId` | 未提及 | 需传实例数据 ID(clone 自 base) | 新增字段 |
  | `level` | 未提及 | Z轴层叠顺序，**必填** | 新增字段 |
  | `base.code` | 注释提到 | 不是请求字段，是读返回才有 | 概念混淆 |
  | `beGroup/beHidden/beLocked` | 未提及 | 应传(含 null 值) | 可选但建议传 |
  | `grade/totalGrade` | 未提及 | 建议传 | 低风险 |

  **重大问题**: 当前注释说 `card = 单个 pageCard（base.code + x/y/w/h + style + data）`，但实际 POST 新增组件时不是传 `base.code`，而是传 `cardId`（组件定义 UUID）。`styleConfigId` 和 `dataId` 的来源也未明确——新建组件时这两个 ID 是由后端 clone 出厂模板自动生成，还是需要客户端先调接口拿到？这是最大的未知项。

- **置信度**: **中** — 最小骨架推断自 level-tree 读结构，但 `styleConfigId/dataId` 的生成机制（是后端自动 clone 还是客户端先取再传）必须通过抓包确认
- **需要抓包确认**: 是

### 4. WK.write.saveCard — 单卡全量保存(autosave)

- **URL**: `POST unity/page-card/{cardId}`
- **当前 wukong-client.js 假设的 body**:
  ```js
  card = 单卡全量（注释："autosave 单卡全量"）
  ```
- **来源佐证**: ENDPOINTS.md 验证 `选中组件实测触发 POST unity/page-card/{cardId} + 重新 GET page-card/level-tree`
- **差异分析**:
  - URL 中的 `{cardId}` 实际应该是 **pageCard 实例 id**（不是组件定义 cardId）—— 这点从端点行为（autosave 针对特定实例）可以推断
  - body 应该是该组件实例的完整 pageCard 对象（含 style/data/interaction 等全量字段）
  - 当前代码 `WK.write.saveCard(cardId, card, opts)` 的参数设计合理（cardId 走 URL，card 走 body）
  - **命名混淆风险**: 参数名 `cardId` 实际是 pageCard 实例 ID，容易和 `card.cardId`（组件定义 ID）混淆，建议改名为 `instanceId` 或 `pageCardId`
- **置信度**: **中-高** — URL 模式和 autosave 行为已验证，body 为全量 pageCard 对象高度可信，但 URL 参数的语义（实例 id vs 定义 id）需抓包确认
- **需要抓包确认**: 是（首次确认 URL 中 id 的语义 + body 是否需要全量还是支持 partial）

### 6. WK.write.saveCardData — 新建数据绑定

- **URL**: `POST unity/card-data`
- **当前 wukong-client.js 假设的 body**:
  ```js
  data = {request, extractor, dataMapping, refresh, cardData, ...}
  // 注释："现有数据对接能力产出"
  ```
- **导出包 §4 cardDataList 字段契约**:
  ```
  id                    - 数据配置 UUID
  name                  - 名称
  type                  - "StaticData" | ...
  proxy                 - 是否走代理
  request               - 15 键请求描述对象 {url, method, body, headers, sourceType, sourceId, categoryName, ...}
  cardData              - 数据样本/静态数据数组
  extractor             - "function filter(data){...}" 清洗脚本
  extractorEnable       - boolean
  paramFilter           - 入参转换脚本
  paramFilterEnable     - boolean
  refreshInterval       - 刷新间隔(ms)，默认 5000
  timeoutTime           - 超时(ms)，默认 6000
  refreshEnable         - boolean
  dataMapping           - 字段映射
  dataMappingEnable     - boolean（当前假设缺失此字段名！）
  testRunConfig         - 测试运行配置
  beControlled          - 是否受控
  ```
- **差异分析**:
  | 字段 | 当前假设 | 导出包/读返回 | 差异 |
  |------|---------|-------------|------|
  | `id` | 缺失 | 新建时可能由后端生成 | 需确认 |
  | `name` | 缺失 | 可选 | 低风险 |
  | `type` | 缺失 | 应传，区分 StaticData/接口类型 | **应补** |
  | `proxy` | 缺失 | 可选 | 低风险 |
  | `extractorEnable` | 注释写 extractorEnable | 字段名一致 | 无差异 |
  | `paramFilter/paramFilterEnable` | 缺失 | 应传（即使空） | 应补 |
  | `dataMappingEnable` | 当前写 dataMapping | 读返回有单独的 `dataMappingEnable` 开关 | **可能遗漏** |
  | `refreshEnable` | 当前写 refresh | 读返回有单独的 `refreshEnable` 开关 | **可能遗漏** |
  | `testRunConfig` | 缺失 | 可选 | 低风险 |
  | `beControlled` | 缺失 | 可选 | 低风险 |

  **核心问题**: 当前注释笼统地写 `{request, extractor, dataMapping, refresh, cardData, ...}`，把启用开关（`extractorEnable`, `paramFilterEnable`, `dataMappingEnable`, `refreshEnable`）混在了对应数据字段里。实际上每个功能特性都有独立的 `xxxEnable` 布尔开关字段，必须显式传。

- **置信度**: **中** — 字段名基本正确但 enable 开关是否必填、新建时 `id` 是否由后端生成均需确认
- **需要抓包确认**: 是

- **findings/07-interactions.md §6 最小记录结构** + **page-interactions.json 42 条实样**:
  ```json
  {
    "pageId": "uuid",
    "name": "交互名称",
    "groupId": "hex32",
    "upstreamType": "CARD",
    "upstream": "uuid(触发源组件ID)",
    "upstreamExtra": null,
    "event": "click",

    "downstream": "uuid(目标组件ID)",
    "downstreamPageId": "uuid|null",
    "downstreamPageType": "PAGE",
    "action": "component",
    "value": "{JSON字符串,含action细节}",
  ```

- **差异分析**:
  - 当前代码只写了 `chain = 页面级交互对象`，未具体列出字段。但 findings 已给出完整 schema + 两套最小模板（模板 A: popup / 模板 B: component request）

- **置信度**: **高** — 42 条真实交互实样 + findings 逆向分析 + 两套最小模板，字段结构完备
- **需要抓包确认**: 否（已有大量实样佐证）

### 关于 batch-import（包补丁路径核心端点）

内部资料 `悟空大项目包或批量大屏导入配置说明.md` 给出了真实的 curl 调用示例：

```bash
# 页面级导入
curl -X POST \
  -H 'Authorization: Bearer <token>' \
  -F 'file=@page_xxxxx.zip' \
  -F 'setStaticData=false' \
  -F 'groupId=<目标分组UUID>' \
  http://localhost:10010/wukong-api/unity/page/batch-import

# 项目级导入
curl -X POST \
  -H 'Authorization: Bearer <token>' \
  -F 'file=@project_xxxxx.zip' \
  -F 'setStaticData=false' \
  -F 'groupId=<目标分组UUID>' \
  http://localhost:10010/wukong-api/unity/project/import
```

**multipart 字段**:
- `file` — zip 文件（page_ 开头 = 页面包，project_ 开头 = 项目包）
- `setStaticData` — 布尔字符串（"false"/"true"），是否设置静态数据
- `groupId` — 目标分组 UUID

**这是内部资料中唯一给出了完整可执行 curl 示例的写端点，置信度极高。**

5. **batch-import** — 内部资料有完整 curl 示例（multipart: file + setStaticData + groupId）

### 需要浏览器抓包确认的关键未知项

1. **newPage**: `project` 字段是否必填？`type` 应传什么值？后端是否要求客户端传 `id`？
2. **addCard**: `styleConfigId` 和 `dataId` 是客户端传还是后端自动 clone？`cardId` 用的是组件定义 UUID 还是 code？
3. **saveCard**: URL 中 `{cardId}` 是 pageCard 实例 id 还是组件定义 id？是否支持 partial update？
4. **saveCardData**: 新建时后端是否自动生成 `id`？`xxxEnable` 开关是否必填？
5. **savePageHook**: 新建 vs 更新如何区分（是否靠 `id` 字段有无）？

### 当前代码中的概念混淆

1. **`base.code` vs `cardId`**: addCard 注释说传 `base.code`，但实际请求应传 `cardId`（组件定义 UUID）
2. **saveCard 的 cardId 参数**: URL 里的 `{cardId}` 其实是 pageCard 实例 ID，应改名避免混淆
3. **enable 开关缺失**: saveCardData 的注释漏掉了 `extractorEnable`/`paramFilterEnable`/`dataMappingEnable`/`refreshEnable` 等独立布尔字段

### interaction/chain 读写同路径

`POST unity/interaction/chain` 既是读（body 仅含 `{pageId}`）又是写（body 含完整交互记录）。这在当前代码中已正确处理（`WK.read.interactions` 和 `WK.write.saveInteraction` 走同一路径），但需要注意：
- 如果要**批量保存**多条交互，可能需要逐条 POST（每条一个请求）
- `value` 字段必须是 **JSON.stringify 后的字符串**，不是对象

## 五、抓包优先级排序

建议在隔离账号上按以下顺序执行手工操作并开 DevTools Network 抓包：

| 优先级 | 操作 | 要抓的端点 | 解决的关键问题 |
|--------|------|-----------|--------------|
| P0 | 新建一个空白页面 | `POST unity/page/` | project 是否必填、type 值、id 生成方 |
| P0 | 在空白页拖入一个组件 | `POST unity/page-card` | cardId vs code、styleConfigId/dataId 生成机制 |
| P1 | 选中组件改属性后点别处(触发 autosave) | `POST unity/page-card/{id}` | URL 中 id 语义、body 是否全量 |
| P1 | 给组件配一个数据源并保存 | `POST unity/card-data` 或 `PUT unity/card-data/{id}` | id 生成、enable 开关必填性 |
| P2 | 编辑页面脚本并保存 | `POST unity/page-hook` | 新建 vs 更新判断逻辑 |
| P2 | 添加一条交互并保存 | `POST unity/interaction/chain` | 确认写入 body 与实样一致 |

## 六、与"包补丁"路径的关系

增量写路径（本报告分析的 `WK.write.*`）是"辅"路径，主路径是"包补丁"（export → 改 pageJson → import）。两条路径的关系：

- **包补丁**: 适合"一句话出整屏"场景，一次性落地全部配置，`batch-import` 端点置信度极高（有内部资料 curl 实例）
- **增量写**: 适合"在既有屏上改/补"场景，需要逐层调用各端点

增量写的校准工作即使完成，也建议优先使用包补丁路径落地（更稳定、字段完整度更高、不怕漏传可选字段）。增量写作为"微调"和"热更新"通道保留。
