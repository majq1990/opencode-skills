# SpEL 示例库

> 用于展示麒舰业务中常见需求表述如何被拆解为场景、条件、主体/字段映射与候选 SpEL，帮助把“业务口语”逐步转成可配置表达式。

## 使用方式

建议把本示例库当作“参考答案库”，而不是死记硬背模板：

1. 先识别需求属于哪个场景
2. 再拆出条件项
3. 用 `spel-subjects.md` 确认主体
4. 用 `spel-fields.md` 确认字段
5. 参考这里的写法组织最终表达式
6. 若值域不明确，优先追问，不要直接编造

> 注意：以下示例主要基于当前资料中已出现的主体与字段整理。示例中的中文值、数字值、节点编码等，部分是“演示写法”，真实配置时应替换为项目实际值。

## 一、菜单场景示例

菜单场景通常关注“是否显示”“是否可见”“是否允许操作”。

### 示例 1：单一案件条件

**需求**：

> 只有投诉来源的案件才显示这个菜单。

**场景识别**：

- 菜单

**条件提取**：

- 问题来源 = 投诉

**主体 / 字段映射**：

- 案件属性 → `#bizEntry`
- 问题来源字段 → `#bizEntry?.eventSrcId` 或 `#bizEntry?.eventSrcName`

**候选 SpEL**：

```spel
#bizEntry?.eventSrcId == 1
```

**说明**：

- 如果系统中“投诉”对应的是名称而不是 ID，也可能写成：

```spel
#bizEntry?.eventSrcName == '投诉'
```

**歧义点**：

- “投诉”到底是名称值还是编码值，需确认。

---

### 示例 2：案件条件 + “阶段/状态”条件

**需求**：

> 问题来源是投诉，且案件处于核实状态时才显示该菜单。

**场景识别**：

- 菜单

**条件提取**：

- 问题来源 = 投诉
- 案件处于某个“核实状态/阶段”

**主体 / 字段映射**：

- 问题来源 → `#bizEntry?.eventSrcId`
- “核实状态/阶段”在菜单场景里不能直接默认写成 `#state`
  - 如果当前项目当前菜单链路已确认提供状态主体，才进一步考虑 `#state?.verifyMsgStateId`
  - 如果这里说的其实是流程中的某个办理环节，则更可能落到 `#actInst?.actDefId` / `#actInst?.actDefName`

**候选 SpEL（仅在已确认菜单链路支持状态主体时才参考）**：

```spel
#bizEntry?.eventSrcId == 1 && #state?.verifyMsgStateId == 4
```

**说明**：

- 这里的 `1`、`4` 都只是示例值。
- 菜单场景里不要因为用户说了“核实状态”“某阶段”，就默认一定可以直接使用 `#state`。
- 更稳妥的做法是先追问：这里到底是业务状态，还是流程节点；当前菜单链路是否真的提供状态主体。

---

### 示例 3：案件条件 + 当前用户条件

**需求**：

> 案件类型是案件类上报，并且当前用户是樊考时才显示。

**场景识别**：

- 菜单

**条件提取**：

- 案件类型 = 某类型
- 当前用户名 = 樊考

**主体 / 字段映射**：

- 案件类型 → `#bizEntry?.recTypeId`
- 当前用户名 → `#username`

**候选 SpEL**：

```spel
#bizEntry?.recTypeId == 1 && #username == '樊考'
```

**说明**：

- 如果要比较的是当前登录账号、部门、区域，不要只用 `#username`，应考虑 `#userDetails`。

---

### 示例 4：用户组织条件

**需求**：

> 只有当前用户属于某部门时才显示该菜单。

**场景识别**：

- 菜单

**条件提取**：

- 当前用户所在部门 = 某部门

**主体 / 字段映射**：

- 当前用户信息 → `#userDetails`
- 部门 → `#userDetails?.unitId` / `#userDetails?.unitName`

**候选 SpEL**：

```spel
#userDetails?.unitName == '监督指挥中心'
```

或：

```spel
#userDetails?.unitId == 'unit_001'
```

**歧义点**：

- 比较部门名称还是部门 ID，需要确认项目实际配置口径。

**主体 / 字段映射**：

### 示例 6：案件条件 + 排除某节点

**需求**：

> 如果问题来源是投诉，且当前不在人工审核节点，就自动批转。

**场景识别**：

- 流程引擎自动批转

**条件提取**：

- 问题来源 = 投诉

**主体 / 字段映射**：

- 问题来源 → `#bizEntry?.eventSrcId`
- 当前节点 → `#actInst?.actDefId`

**候选 SpEL**：

```spel
#bizEntry?.eventSrcId == 1 && #actInst?.actDefId != 'artificial_597c44be-382c-462d-ad12-f0ffb7ba7407'
```

**说明**：

- 这里沿用了资料中已出现过的 `#actInst?.actDefId != 'artificial_...'` 写法。
- “人工审核节点”是否真的对应这个编码，必须结合真实流程配置确认。

---

### 示例 7：只在某节点允许自动流转

**需求**：

**场景识别**：

**主体 / 字段映射**：

- 当前节点 → `#actInst?.actDefId` 或 `#actInst?.actDefName`

**候选 SpEL**：

```spel

```

或：

```spel
#actInst?.actDefName == '受理'
```

**歧义点**：

- 节点比较时，最容易不明确的是“节点名称”还是“节点编码”。

---

### 示例 8：流程条件 + 用户条件

**需求**：

> 当前节点是核查环节，并且当前办理人为某人时，进入指定流程分支。

**主体 / 字段映射**：

**候选 SpEL**：

```spel
#actInst?.actDefName == '核查' && #actInst?.humanName == '张三'
```

## 三、案件显示样式场景示例

该场景关注“标红、高亮、标签、颜色”等展示效果，但 SpEL 一般只负责命中条件。

### 示例 9：单一案件条件触发标红

**需求**：

> 投诉来源案件在列表里标红。

**场景识别**：

- 案件显示样式

**条件提取**：

- 问题来源 = 投诉

**主体 / 字段映射**：

- 问题来源 → `#bizEntry?.eventSrcId`

**候选 SpEL**：

```spel
#bizEntry?.eventSrcId == 1
```

**命中效果说明**：

- 命中后“标红”通常在样式配置项中定义，不写进 SpEL 本身。

---

### 示例 10：状态条件触发高亮

**需求**：

> 核实状态为待核实的案件高亮显示。

**场景识别**：

- 案件显示样式

**条件提取**：

- 核实状态 = 待核实

**主体 / 字段映射**：

- 在 MIS 样式计划等已确认链路中，可优先考虑核实状态 → `#state?.verifyMsgStateId`
- 若当前项目不是这类已确认提供 `#state` 的样式链路，则不应把 `#state` 当成无争议通用主体

**候选 SpEL（仅在已确认样式链路支持状态主体时才参考）**：

```spel
#state?.verifyMsgStateId == 4
```

**歧义点**：

- “待核实”是否真的对应 `4`，需要按项目值域确认。
- 当前场景是否就是 MIS 样式计划或其他已确认提供 `#state` 的链路，也需要先确认。

---

### 示例 11：案件条件 + 状态条件联合样式

**需求**：

> 投诉来源且当前处于受理阶段的案件，用特殊颜色显示。

**场景识别**：

- 案件显示样式

**条件提取**：

- 问题来源 = 投诉
- 当前阶段 = 受理阶段

**主体 / 字段映射**：

- 问题来源 → `#bizEntry?.eventSrcId`
- “阶段”可能是状态，也可能是流程节点

**候选 SpEL（按状态理解）**：

```spel
#bizEntry?.eventSrcId == 1 && #state?.verifyMsgStateId == 4
```

**候选 SpEL（按流程节点理解）**：

```spel
#bizEntry?.eventSrcId == 1 && #actInst?.actDefName == '受理'
```

**说明**：

- 这里不能直接断定“受理阶段”属于 `#state` 还是 `#actInst`，属于应优先追问的歧义。

---

### 示例 12：时间条件触发样式

**需求**：

> 已超时案件高亮显示。

**场景识别**：

- 案件显示样式

**条件提取**：

- 已超时

**主体 / 字段映射**：

- 时间 / 时限条件不能直接默认写成统一的 `#timing`
- 若当前项目当前链路明确提供统一 timing 主体，才进一步考虑类似 `#timing?.remain`
- 若当前场景是 MIS 样式扩展链路，也可能实际通过 `#actInstTiming` 等扩展上下文承载时限信息

**候选 SpEL（仅作示意，不表示已统一确认支持）**：

```spel
#timing?.remain <= 0
```

**说明**：

- 当前资料没有确认统一稳定的 `#timing` 主体注入点，因此这里的写法只能作为“可能的表达方式示意”，不能包装成所有样式场景的通用标准写法。
- 若项目里“超时”的定义更复杂，应先确认是按剩余时限、警告阈值，还是按 MIS 样式扩展上下文中的具体字段判断。

## 四、消息配置 / 规则配置场景示例

该场景通常关注“是否触发提醒”“是否命中规则”“是否发送消息”。

### 示例 13：单条件消息触发

**需求**：

> 投诉来源案件触发提醒消息。

**场景识别**：

- 消息配置 / 规则配置

**条件提取**：

- 问题来源 = 投诉

**主体 / 字段映射**：

- 问题来源 → `#bizEntry?.eventSrcId`

**候选 SpEL**：

```spel
#bizEntry?.eventSrcId == 1
```

---

### 示例 14：案件条件 + 状态条件触发提醒

**需求**：

> 投诉来源案件在核实状态下发送提醒。

**场景识别**：

- 消息配置 / 规则配置

**条件提取**：

- 问题来源 = 投诉
- 核实状态 = 某状态

**主体 / 字段映射**：

- 问题来源 → `#bizEntry?.eventSrcId`
- 核实状态
  - 若当前链路已确认提供状态主体，可进一步考虑 `#state?.verifyMsgStateId`
  - 若这里说的其实是流程环节中的“某阶段”，也要先和 `#actInst` 节点条件区分

**候选 SpEL（仅在已确认当前消息 / 规则链路支持状态主体时才参考）**：

```spel
#bizEntry?.eventSrcId == 1 && #state?.verifyMsgStateId == 4
```

**说明**：

- `#state` 在 MIS 规则 provider 等相关链路里证据更强，但不应直接包装成所有消息 / 规则场景都默认统一支持。
- 若用户说的“核实状态”实际是某个流程环节，应优先改按 `#actInst` 理解。

### 示例 16：时间类规则触发

**需求**：

> 超时未处理时发送通知。

**场景识别**：

- 消息配置 / 规则配置

**条件提取**：

- 已超时
- 未处理（若项目需要，还要补充对应状态字段）

**主体 / 字段映射**：

- “超时”不能直接默认写成统一的 `#timing`
  - 若当前项目当前链路明确提供统一 timing 主体，才进一步考虑类似 `#timing?.remain`
  - 在部分 MIS 相关链路里，也可能通过其他时限上下文承载，而不是统一 `#timing`
- “未处理”可能是 `#state`，也可能是流程节点或其他业务状态字段

**候选 SpEL（仅作示意，不表示已统一确认支持）**：

```spel
#timing?.remain <= 0
```

**候选 SpEL（超时 + 某处理状态，仍仅作示意）**：

```spel
#timing?.remain <= 0 && #state?.disposeState == 0
```

**歧义点**：

- “未处理”到底对应哪个字段，当前资料未直接给出统一结论，需按项目口径确认。
- 当前链路是否真的提供统一 `#timing` 主体，也必须先确认。

## 五、可直接复用的组合示例

下面这些更适合作为“写法模板”参考。

### 1. 单条件等值判断

```spel
#bizEntry?.recTypeId == 1
```

### 2. 单条件不等判断

```spel
#actInst?.actDefId != 'artificial_597c44be-382c-462d-ad12-f0ffb7ba7407'
```

### 3. 两个条件同时满足

```spel
#bizEntry?.recTypeId == 1 && #bizEntry?.eventSrcId == 1
```

### 4. 两个条件任一满足

```spel
#bizEntry?.recTypeId == 1 || #bizEntry?.recTypeId == 2
```

### 5. 案件条件 + 用户条件

```spel
#bizEntry?.recTypeId == 1 && #username == '樊考'
```

### 6. 状态条件（仅在已确认支持状态主体的链路中参考）

```spel
#state?.verifyMsgStateId == 4
```

## 六、必须先追问的示例

这些情况并非不能生成，而是不应在信息不足时直接生成表达式。

### 示例 17：值不明确

**需求**：

> 问题来源是投诉时显示。

**为什么要追问**：

- “投诉”到底对应 `eventSrcId` 还是 `eventSrcName`
- 如果是 `eventSrcId`，具体值是多少

**推荐追问**：

- “这里的‘投诉’您希望按来源名称比较，还是按来源编码比较？”
- “如果按编码比较，投诉对应的实际值是多少？”

---

### 示例 18：“阶段”含义不明确

**需求**：

> 案件在受理阶段时发送消息。

**为什么要追问**：

- “受理阶段”可能指状态，也可能指流程节点

**推荐追问**：

- “这里的‘受理阶段’是指某个状态值，还是指流程里的某个节点/环节？”
- “如果是节点，您这边有对应的节点编码或节点名称吗？”

---

### 示例 19：超时口径不明确

**需求**：

> 快超时的时候高亮显示。

**为什么要追问**：

- “快超时”缺少明确阈值
- 不清楚按剩余小时、警告时间还是其他规则判断

**推荐追问**：

- “这里的‘快超时’是指剩余多少小时以内，还是以警告时间作为触发条件？”
- “如果按剩余时间判断，具体阈值是多少？”

---

### 示例 20：谁触发和谁接收混在一起

**需求**：

> 投诉来源案件给监督中心的人发消息。

**为什么要追问**：

- SpEL 通常只负责“是否触发”
- “发给谁”往往是接收人配置，不一定属于表达式本身

**推荐追问**：

- “这里我先帮您拆成两部分：一部分是‘投诉来源案件是否触发’，另一部分是‘接收人配置’。当前您是希望先生成触发条件表达式，对吗？”

---

## 七、可带假设生成的示例

以下情况如果用户没有给足信息，可以先带着假设给候选表达式，但必须明确写出假设。

### 示例 21：按名称先生成

**需求**：

> 当前用户属于监督中心时可见。

**可带假设生成**：

- 假设比较部门名称

**候选 SpEL**：

```spel
#userDetails?.unitName == '监督中心'
```

**应附带说明**：

- “这里先假设您是按部门名称比较；如果实际需要按部门 ID 比较，请替换为 `unitId` 对应值。”

---

### 示例 22：按节点名称先生成

**需求**：

> 到核查环节时触发规则。

**可带假设生成**：

- 假设项目允许直接按节点名称比较

**候选 SpEL**：

```spel
#actInst?.actDefName == '核查'
```

**应附带说明**：

- “这里先按节点名称生成；如果实际配置要求使用节点编码，请改为 `actDefId`。”

---

## 八、推荐输出范式示例

当 skill 真正对外输出时，建议尽量按这种结构组织，而不是只扔一个表达式。

### 范式示例 1

**需求**：

> 投诉来源案件在核实状态时发送提醒。

**推荐输出**：

- 场景识别：消息配置 / 规则配置
- 条件提取：
  - 问题来源 = 投诉
  - 核实状态 = 某状态值
- 主体 / 字段映射：
  - 问题来源 → `#bizEntry?.eventSrcId`
  - 核实状态 → 若当前链路已确认提供状态主体，可进一步考虑 `#state?.verifyMsgStateId`
- 假设项：
  - 假设“投诉”对应来源 ID = `1`
  - 假设当前链路已确认支持 `#state`
  - 假设目标核实状态值 = `4`
- 候选 SpEL：

```spel
#bizEntry?.eventSrcId == 1 && #state?.verifyMsgStateId == 4
```

- 触发逻辑说明：
  - 仅当案件来源为投诉，且当前链路确实提供状态主体、核实状态满足指定值时，才命中该提醒规则。

---

### 范式示例 2

**需求**：

> 只有监督中心的人处理投诉来源案件时，这个菜单才显示。

**推荐输出**：

- 场景识别：菜单
- 条件提取：
  - 当前用户所属部门 = 监督中心
  - 问题来源 = 投诉
- 主体 / 字段映射：
  - 当前用户部门 → `#userDetails?.unitName`
  - 问题来源 → `#bizEntry?.eventSrcId`
- 假设项：
  - 假设按部门名称比较
  - 假设“投诉”对应来源 ID = `1`
- 候选 SpEL：

```spel
#userDetails?.unitName == '监督中心' && #bizEntry?.eventSrcId == 1
```

- 触发逻辑说明：
  - 当前用户属于监督中心，且案件来源为投诉时，菜单可见。

## 九、常见错误写法对照

### 错误 1：把中文业务词直接当字段名

**错误写法**：

```spel
#bizEntry?.问题来源 == '投诉'
```

**正确思路**：

- 应先映射到真实字段，如 `eventSrcId` 或 `eventSrcName`

---

### 错误 2：把 `#username` 当对象使用

**错误写法**：

```spel
#username?.name == '樊考'
```

**正确写法**：

```spel
#username == '樊考'
```

---

### 错误 3：把流程节点误写成状态字段

**错误写法**：

```spel
#state?.actDefId == 'accept_node'
```

**正确思路**：

- 流程节点通常优先看 `#actInst`

---

### 错误 4：把 `#timing` 当成已统一确认的通用主体

**错误思路**：

- 只要需求里提到“超时”，就直接默认所有场景都能写 `#timing`

**错误写法**：

```spel
#timing?.deadlineTime < now()
```

**正确思路**：

- 当前 research 尚未确认统一稳定的 `#timing` 主体注入点
- 时间条件应先确认当前链路到底提供统一 `#timing`，还是通过其他上下文（如 MIS 样式扩展对象）承载
- 即使引用 `#timing` 示例，也应明确它只是候选或示意，不应包装成全场景通用定论

---

## 十、结论性提示

从业务口语生成 SpEL 时，最重要的不是“马上拼表达式”，而是按顺序完成这几步：

1. 先识别场景
2. 再拆条件
3. 再选主体
4. 再找字段
5. 最后确认比较值口径

如果“字段不明确、值不明确、阶段含义不明确、超时口径不明确”，应优先追问；如果只是名称/编码未确认，可以在明确假设的前提下先给候选表达式。
