# Egova 业务 SpEL 表达式生成与场景索引

## 适用场景

该 skill 用于 Egova / EUrban / MIS 业务配置中的 SpEL 场景识别、主体选择、字段映射与候选表达式生成。

核心原则：**先识别场景，再确认主体与字段；能生成就先给候选表达式，不能可靠生成再追问。**

在这些情况优先使用本 skill：

- 写、改、解释、校验 Egova 业务里的 SpEL 表达式
- 判断某个场景一般支持哪些主体、占位符、上下文对象
- 把业务口语规则整理成可配置条件
- 处理菜单 / 按钮显示条件
- 处理流程自动批转 / 自动流转 / 分支条件
- 处理案件标红 / 高亮 / 标签 / 样式命中条件
- 处理消息提醒 / 通知 / 规则命中条件
- 判断 `#bizEntry`、`#actInst`、`#state`、`#userDetails`、`#username`、`#timing` 怎么选

以下情况不要包装成最终定论：

- 当前场景是否支持某主体还没确认
- 需求涉及文档中未出现的新字段或新主体
- 用户真正要问的是底层代码是否注入了某主体

## 使用方式

按下面顺序处理：

1. **识别场景**
   - 菜单
   - 流程引擎自动批转
   - 案件显示样式
   - 消息配置 / 规则配置
2. **确认主体范围**
   - 先看场景文档，不跨场景硬套主体
3. **拆分业务条件**
   - 如来源、类型、节点、状态、当前用户、时间条件
4. **映射主体与字段**
   - 只用项目资料中已出现过的主体和字段路径
5. **判断关键歧义**
   - 如场景、阶段含义、值域、名称/编码口径
6. **选择输出模式**
   - 信息不足 → 追问模式
   - 信息足够 → 生成模式
7. **输出结果并说明假设 / 确认点**

### 输出模式

不要每次都输出同一套大模板。

#### 模式 A：信息不足

适用于仍缺关键场景、主体、字段或值域时。

输出：
- 场景识别
- 已识别条件
- 歧义点
- 最少必要追问项

要求：
- 只问继续生成所必须的问题
- 若仅缺 1~2 个关键值，优先一次性问完
- 不要展开式连环追问

#### 模式 B：可生成

适用于已能给出可靠候选表达式时。

输出：
- 场景识别
- 条件提取
- 主体 / 字段映射
- 假设项（如有）
- 最终 SpEL
- 结果说明
- 需用户确认点（如有）

要求：
- 默认优先给 **1 条主推荐表达式**
- 若存在常见分歧，可再给 **1 条备选表达式**
- 分析要服务于表达式生成，不要只停留在解释

### 工作规则

#### 1. 先识别场景

不要在还没判断是菜单、流程、样式还是消息规则时直接写表达式。

参考：`references/scene-index.md`

#### 2. 先确认主体，再写表达式

不同项目、子系统、场景对主体支持范围不同。避免这些误用：

- 把 MIS 中的 `#state` 推广成所有 core 场景默认主体
- 因为需求涉及超时，就把 `#timing` 当成已统一确认主体
- 把部分链路中的 `#userDetails`、`#username` 无条件推广到所有规则场景

先看场景文档，再看主体文档；必要时再回到 research / 代码证据。

#### 3. 先拆条件，再组织逻辑

- 同时满足 → `&&`
- 任一满足 → `||`
- 排除条件 → `!=` 或整体取反

#### 4. 只使用可映射字段

不要把中文业务词直接写成字段名。优先使用 references 中已出现的字段路径。

#### 5. 关键歧义先追问，非关键歧义可带假设生成

必须优先追问的典型情况：

- 场景不明确
- “阶段”不明确是状态还是流程节点
- 比较的是名称还是编码
- 值域缺失且会直接影响表达式正确性

可以带假设先生成的典型情况：

- 场景明确、字段大致明确，只缺名称/编码口径
- 用户明确表示先给候选写法即可

#### 6. 产出优先

如果信息已经足够，不要只做分析，要给候选表达式。

默认策略：
- 先给 1 条主推荐表达式
- 有必要时补 1 条备选表达式
- 再说明假设、歧义和确认点

### 示例

**需求**：

> 投诉来源案件在受理阶段时才显示这个菜单。

**推荐输出（模式 B）**：

#### 场景识别
- 菜单

#### 条件提取
- 问题来源 = 投诉
- 当前处于受理阶段

#### 主体 / 字段映射
- 问题来源通常优先看 `#bizEntry?.eventSrcId` / `#bizEntry?.eventSrcName`
- “受理阶段”不能直接默认落到 `#state`
  - 如果这里指流程节点，更可能看 `#actInst?.actDefId` / `#actInst?.actDefName`
  - 如果当前链路已确认提供状态主体，才进一步考虑 `#state`

#### 假设项
- 假设“投诉”按来源 ID 比较，值为 `1`
- 假设“受理阶段”按流程节点名称比较，节点名为 `受理`

#### 最终 SpEL
```spel
#bizEntry?.eventSrcId == 1 && #actInst?.actDefName == '受理'
```

#### 结果说明
- 该表达式表示：案件来源为投诉，且当前流程环节为受理时，菜单可见。

#### 需用户确认点
- “投诉”是否应按 ID 比较
- “受理阶段”是否实际是节点而不是状态

### Guardrails

- 不编造项目中不存在的新主体或新字段
- 不把局部链路能力包装成全项目通用能力
- 不把 MIS 里的 `#state` 直接写成所有 core 场景默认主体
- 不把 `#timing` 写成已统一确认支持的主体，除非当前链路已有明确证据
- 假设必须显式写出，不能伪装成已确认事实
- 如果用户要确认最终支持范围，应提示回看项目文档、research 或代码实现

### Common Mistakes

- 不区分场景，直接套表达式
- 不确认主体范围，就直接使用 `#state` / `#timing`
- 把中文业务词直接翻写成字段名
- 需求明显不完整，却不追问
- 信息已经足够，却只分析不给表达式
- 不说明假设，却输出看似确定的结果

### Boundaries

该 skill 主要用于：

- 解释各场景下通常可关注的主体、占位符与字段语义
- 根据业务描述生成项目内可落地的候选 SpEL
- 在描述模糊时辅助追问和梳理

该 skill 不负责：

- 替代代码调研确认最终注入范围
- 修改底层 SpEL 注入逻辑
- 保证文档外字段一定可用

最终支持范围仍应以项目资料、research 和代码实现为准。
