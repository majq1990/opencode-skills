# 输出格式规范

> 用途：定义最终答复和信息缺失时的输出形态。

## 需求不完整时

需求不完整时使用所有环境通用的 Markdown 文本卡片：可枚举缺口用 `### 请选择`，长文本资料用 `### 请补充`。不输出方案、字段映射或过滤脚本。目标是保留用户已经给出的上下文，只让用户回复选项字母或按编号补缺口，不要求重新发送完整需求。A/B/C/D 选项必须写成编号项下面的嵌套无序列表（`- A. ...`），不能顶格，也不要只用空格加 `A.` 文本；默认建议项放 A 且不标注“推荐”，最后一个选项保留“其他，请说明：____”。

```text
### 已确认
- 业务域/对象：...
- 展示目标：...
- 统计口径：...
- 时间范围：...
- 输出粒度：...
- 数据源状态：...

### 请选择
1. 数据来源路径：____
   - A. 暂无接口但有表/查询逻辑
   - B. 现场已有接口
   - C. 接口和表都不明确
   - D. 其他，请说明：____

2. 组件静态模板状态：____
   - A. 无模板
   - B. 有模板，稍后粘贴
   - C. 不确定
   - D. 其他，请说明：____

### 请补充
3. 接口完整返回样例：____（如选择现场已有接口，必须包含 {hasError,result,message,tag,totalCount} 外层）
4. 表字段清单：____（如选择表/查询逻辑，请提供表名、字段名、字段含义）

请直接回复选项字母，或按编号补空白；补齐后我再继续生成字段映射和过滤脚本。
```

不需要的选择题或填空项可以省略，但保留 `### 已确认`；多个清单连续出现时，序号必须全局连续。

## 需求足够时

默认只输出四段：

1. `结论`：推荐数据源、业务域、业务对象、接口类型、接口名称、请求方式、接口地址、星桥接口路径地址、推荐 `result` 数据格式、默认假设。
2. `映射`：原始来源字段到目标组件字段的映射表；结构一致时说明无需复杂转换，只做空值兜底。
3. `过滤脚本`：完整 ES5 `function filter(data)`。
4. `需要核对的内容`：只列落地前需要现场核对的联调事项；没有则写“无”。它不是继续向用户索要阻塞信息的入口，也不要求用户当前必须回复。若缺失信息会影响接口入参、返回结构、SQL、映射或脚本正确性，必须停在 `### 请补充` 并让用户按编号补齐，不能输出最终四段式。

## 默认假设放置位置

非阻塞默认假设写入“结论”的默认假设中，例如：

- 默认不限制筛选条件；
- 默认统计所有区域；
- 默认行政层级；
- 表 / SQL fallback 的普通聚合查询默认按 MySQL 兼容 SQL 编写；
- `filter(data)` 默认接收公司响应外层的 `result` 本体。

不要把这些非阻塞默认项放到“需要核对的内容”。“需要核对的内容”只表示需要核对的内容；如果需要用户继续输入才能生成正确方案，必须改用 `### 请补充` 并停止。

## 禁止输出

除非用户明确要求，不输出：

- 需求摘要；
- PRD；
- 计划；
- 完整思考过程；
- 未确认字段的假设接口示例；
- 与当前业务无关的示例接口。
