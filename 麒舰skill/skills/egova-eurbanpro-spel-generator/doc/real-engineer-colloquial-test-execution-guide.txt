Egova SpEL 技能验证用——测试执行清单、判分标准与理想回答示例

说明：
1. 本文件是对《real-engineer-colloquial-test-samples.txt》的升级版补充，用于把“样例集”进一步变成可执行的验证文档。
2. 原样例集负责提供测试输入；本文件负责指导“怎么测、怎么判、什么回答算理想”。
3. 建议使用方式：测试时同时打开以下两个文件：
   - real-engineer-colloquial-test-samples.txt
   - 本文件
4. 本文件主要包括四部分：
   - 测试前准备清单
   - 单条样例执行清单
   - 判分标准
   - 代表性理想回答示例

==================================================
一、测试目标
==================================================

本轮验证重点不是检查模型会不会“随便拼一个 SpEL”，而是检查它是否具备工程可用性，具体包括：

1. 能否先识别场景
2. 能否从口语中拆出条件
3. 能否克制地选择主体与字段
4. 能否在关键信息不够时先追问
5. 能否在适合时带假设生成，而不是伪装成最终答案
6. 能否输出工程人员可直接理解和继续配置的结果

==================================================
二、测试前准备清单
==================================================

每次正式验证前，先按以下清单确认：

[ ] 1. 已准备好当前 skill 主文件：SKILL.md
[ ] 2. 已准备好场景文档：
      - references/scene-index.md
      - references/scene-menu.md
      - references/scene-workflow-auto-transfer.md
      - references/scene-case-display-style.md
      - references/scene-message-rule.md
[ ] 3. 已准备好支撑文档：
      - references/ambiguity-handling.md
      - references/spel-subjects.md
      - references/spel-fields.md
      - references/spel-examples.md
[ ] 4. 已准备好原始样例集：real-engineer-colloquial-test-samples.txt
[ ] 5. 已确定本轮测试范围：
      - 仅测场景识别
      - 或测追问质量
      - 或测带假设生成
      - 或测完整输出质量
[ ] 6. 已确定记录方式：
      - 手工记录到 txt / md
      - 或直接在测试表中打分
[ ] 7. 已统一判分口径，避免同一类错误前后标准不一致

建议：
- 第一轮只做“场景识别 + 处理方式判断”
- 第二轮再做“字段映射 + 表达式生成”
- 第三轮再做“完整结构化输出质量”

==================================================
三、单条样例执行清单
==================================================

每测一条样例，建议严格按以下步骤执行。

步骤 1：读取样例基本信息
- 记录样例编号
- 记录场景类别
- 记录用户口语输入
- 记录期望处理方式
- 记录验证重点

步骤 2：把“用户口语输入”原样喂给 skill
- 不要先替 skill 做二次润色
- 不要提前把字段名或主体名告诉 skill
- 尽量模拟真实工程人员自然输入

步骤 3：记录 skill 输出
至少记录以下内容：
- 是否识别了场景
- 是否提取了条件
- 是否指出歧义
- 是否先追问 / 带假设 / 直接生成
- 是否给出候选 SpEL
- 是否附带中文说明

步骤 4：对照原样例的“期望处理方式”
重点检查：
- 应先追问的，是否没有直接乱写
- 应带假设生成的，是否明确写了假设
- 应直接生成的，是否没有过度追问

步骤 5：按本文件第四部分进行打分
- 先给分项分
- 再给总分
- 最后记录主要问题

步骤 6：记录结论标签
建议使用以下标签之一：
- 通过
- 基本通过
- 需修订
- 明显失败

步骤 7：若失败，标注应反哺的文档位置
可优先回补到：
- references/ambiguity-handling.md
- references/spel-examples.md
- references/spel-fields.md
- 对应 scene-*.md
- SKILL.md

==================================================
四、判分标准
==================================================

建议单条样例满分 10 分。

一共分 5 个维度，每项 0-2 分。

--------------------------------------------------
1. 场景识别（0-2 分）
--------------------------------------------------

2 分：
- 场景识别正确
- 且没有把相近场景混淆

1 分：
- 大方向接近
- 但表述不够稳，或存在轻微混淆

0 分：
- 场景识别错误
- 或场景本应先追问却直接默认成某个场景

常见扣分点：
- 把菜单误判成消息规则
- 把样式误判成菜单
- 把自动批转误判成普通条件过滤

--------------------------------------------------
2. 条件拆解（0-2 分）
--------------------------------------------------

2 分：
- 能完整拆出关键条件
- 能识别与 / 或 / 非 / 排除 / 取反逻辑

1 分：
- 拆出了一部分条件
- 但遗漏一个关键条件或逻辑关系不够明确

0 分：
- 条件拆解明显错误
- 或把效果、动作、接收人错当成触发条件

常见扣分点：
- 漏掉“并且”“或者”
- 漏掉“不要显示”中的取反语义
- 把“标红”“发给谁”“走指定分支”直接写进 SpEL 条件里

--------------------------------------------------
3. 主体 / 字段映射（0-2 分）
--------------------------------------------------

2 分：
- 主体选择合理
- 字段映射克制
- 没有臆造新字段

1 分：
- 主体大致合理
- 但字段口径说明不足，或对多个候选主体的区分不够清楚

0 分：
- 直接臆造字段名
- 或明显把条件映射到错误主体

常见扣分点：
- 把中文业务词直接当字段名
- 用 #state 表达流程节点
- 把 #username 当对象用
- 不区分 #userDetails、#username、#actInst?.humanName

--------------------------------------------------
4. 歧义处理（0-2 分）
--------------------------------------------------

2 分：
- 关键歧义时能先追问
- 非关键歧义时能明确假设后再生成

1 分：
- 能意识到存在歧义
- 但追问不够到点，或假设写得不够明确

0 分：
- 关键信息不明时直接编造表达式
- 或把假设包装成确定事实

常见扣分点：
- “受理阶段”未区分状态还是节点
- “投诉”未区分名称还是编码
- “快超时”未追问阈值
- “特殊案件”未追问判定规则

--------------------------------------------------
5. 输出结构与工程可用性（0-2 分）
--------------------------------------------------

2 分：
- 输出结构清晰
- 至少包含场景识别、条件提取、主体/字段映射、追问/假设、候选 SpEL、中文说明中的大部分内容
- 工程人员看后可继续配置

1 分：
- 有表达式，也有少量解释
- 但结构不完整或工程解释不足

0 分：
- 只扔一个表达式
- 或输出非常混乱，无法直接用于配置讨论

常见扣分点：
- 只输出一行 SpEL
- 没有解释假设
- 没有说明为什么这样选主体

--------------------------------------------------
总分结论建议
--------------------------------------------------

9-10 分：通过
- 可认为该类口语输入处理较稳定

7-8 分：基本通过
- 能用，但仍建议补充措辞或歧义处理规则

4-6 分：需修订
- 存在明显短板，应反向修订 skill 文档

0-3 分：明显失败
- 当前 skill 对该类输入支持不足，不适合直接用于真实工程场景

==================================================
五、快速失败判定规则
==================================================

出现以下任一情况，建议本条样例直接判为“需修订”或“明显失败”：

1. 在应先追问的情况下，直接编造字段并给出表达式
2. 把中文业务词直接写成字段名
3. 把样式效果、动作结果、接收人配置错误写进 SpEL 条件
4. 明显混淆状态与流程节点
5. 用户已表达“先按常见写法”，但 skill 仍把假设写成确定事实
6. 输出完全无结构，只给一条表达式且没有任何解释

==================================================
七、代表性理想回答示例
==================================================

以下示例不是要求措辞逐字一致，而是用于说明“什么样的回答更接近理想状态”。

--------------------------------------------------
示例 1：带假设生成型
对应样例：[MENU-01]
--------------------------------------------------

用户口语输入：
这个菜单只给投诉来源的案件显示。

理想回答示例：
- 场景识别：菜单
- 条件提取：
  - 问题来源 = 投诉
- 主体 / 字段映射：
  - 案件信息通常优先看 `#bizEntry`
  - “问题来源”可优先考虑 `#bizEntry?.eventSrcId` 或 `#bizEntry?.eventSrcName`
- 歧义点：
  - “投诉”这里可能是来源名称，也可能是来源编码
- 假设项：
  - 这里先假设按来源名称比较
- 候选 SpEL：
```spel
#bizEntry?.eventSrcName == '投诉'
```
- 另一种常见写法：
```spel
#bizEntry?.eventSrcId == 1
```
- 中文说明：
  - 该表达式用于控制菜单可见性，仅当案件来源满足“投诉”时显示。
  - 如果你们项目里“投诉”实际使用编码值，请把示例中的名称或数字替换成真实值。

理想点说明：
- 正确识别菜单场景
- 能提到 #bizEntry
- 不武断认定“投诉”一定是 1
- 有假设声明

--------------------------------------------------
示例 2：直接生成型
对应样例：[MENU-07]
--------------------------------------------------

用户口语输入：
我这边想让案件类上报的单子，并且当前登录人是樊考时，菜单可见。

理想回答示例：
- 场景识别：菜单
- 条件提取：
  - 案件类型 = 案件类上报
  - 当前登录人 = 樊考
- 主体 / 字段映射：
  - 案件类型可优先考虑 `#bizEntry?.recTypeId`
  - 当前登录人可优先考虑 `#username`
- 候选 SpEL：
```spel
#bizEntry?.recTypeId == 1 && #username == '樊考'
```
- 中文说明：
  - 仅当案件属于“案件类上报”，且当前登录用户名为“樊考”时，菜单可见。
  - 其中 `1` 需要替换成你们项目里“案件类上报”的实际类型值。

理想点说明：
- 这是信息相对充分的场景，可直接给候选表达式
- 但仍需提醒 recTypeId 的实际值要核对
- 不是只扔表达式，而是有结构化解释

--------------------------------------------------
示例 3：必须先追问型
对应样例：[MENU-05]
--------------------------------------------------

用户口语输入：
这个功能不要给受理阶段的案件显示。

理想回答示例：
- 场景识别：菜单
- 已识别条件：
  - 存在“不要显示”的取反逻辑
  - 条件核心词为“受理阶段”
- 关键歧义：
  - “受理阶段”这里需要先确认，它是指某个状态值，还是指流程里的某个节点/环节
- 建议先确认：
  1. 你这里的“受理阶段”是状态，还是流程节点？
  2. 如果是状态，对应的字段和值是什么？
  3. 如果是流程节点，是按节点名称还是节点编码比较？
- 暂不直接生成表达式原因：
  - 当前还不能确定应该使用 `#state` 还是 `#actInst`，此时直接输出 `!=` 表达式风险较大。

理想点说明：
- 识别到取反逻辑
- 没有急着输出错误表达式
- 追问问题打在关键歧义点上

--------------------------------------------------
示例 4：流程自动批转型
对应样例：[FLOW-02]
--------------------------------------------------

用户口语输入：
如果是投诉，而且当前不在人工审核节点，就走自动流转。

理想回答示例：
- 场景识别：流程引擎自动批转
- 条件提取：
  - 问题来源 = 投诉
  - 当前节点 != 人工审核节点
- 主体 / 字段映射：
  - 问题来源可优先看 `#bizEntry`
  - 流程节点可优先看 `#actInst`
- 假设项：
  - 先假设“投诉”按来源编码比较
  - 先假设“人工审核节点”按节点编码比较
- 候选 SpEL：
```spel
#bizEntry?.eventSrcId == 1 && #actInst?.actDefId != 'artificial_597c44be-382c-462d-ad12-f0ffb7ba7407'
```
- 中文说明：
  - 该表达式仅用于判断是否命中自动流转条件。
  - 它不直接表示最终会流转到哪个节点。
  - 其中来源值与节点编码都应替换为项目实际值。

理想点说明：
- 没把它误识别成菜单
- 能拆出排除节点条件
- 能说明表达式只负责命中条件

--------------------------------------------------
示例 5：样式条件型
对应样例：[STYLE-04]
--------------------------------------------------

用户口语输入：
超时的都高亮出来。

理想回答示例：
- 场景识别：案件显示样式
- 条件提取：
  - 已超时
- 主体 / 字段映射：
  - 时间类条件通常优先考虑 `#timing`
- 假设项：
  - 这里先按“remain <= 0”理解为已超时
- 候选 SpEL：
```spel
#timing?.remain <= 0
```
- 中文说明：
  - 该 SpEL 只负责判断是否命中“高亮”条件。
  - 具体高亮成什么颜色，通常在样式配置项中定义，不写在表达式里。
  - 如果你们项目对“超时”还有更复杂口径，需要再按实际字段调整。

理想点说明：
- 能区分“高亮”是效果，不是条件本身
- 能联想到 #timing
- 能说明超时口径可能需要按项目确认

--------------------------------------------------
示例 6：消息规则 + 接收人拆分型
对应样例：[MSG-05]
--------------------------------------------------

用户口语输入：
投诉案件给监督中心的人发消息。

理想回答示例：
- 场景识别：消息配置 / 规则配置
- 初步拆解：
  - 触发条件：投诉案件
  - 接收人配置：监督中心的人
- 关键提醒：
  - SpEL 一般优先负责“是否命中触发条件”
  - “发给谁”通常需要在接收人配置中单独设置，不建议直接混写进触发条件表达式
- 如果你当前是想先生成触发条件，可先写成：
```spel
#bizEntry?.eventSrcId == 1
```
- 但在正式落表达式前，建议先确认：
  1. “投诉”是按名称还是编码比较？
  2. 你现在要我先帮你写“触发条件”，还是连“接收人规则”也一起梳理？

理想点说明：
- 能把“触发条件”和“接收人配置”拆开
- 不把“监督中心的人”硬塞进 SpEL
- 追问点合理

--------------------------------------------------
示例 7：高歧义混合型
对应样例：[MIX-01]
--------------------------------------------------

用户口语输入：
帮我写个只有符合条件才生效的 SpEL。

理想回答示例：
- 当前信息还不足以直接生成表达式，原因是场景尚未明确。
- 我需要先确认这个 SpEL 是用于哪一类配置：
  1. 菜单 / 按钮可见性
  2. 流程引擎自动批转
  3. 案件显示样式
  4. 消息配置 / 规则触发
- 不同场景下，可用主体和字段重点会不一样；场景不明确时直接生成，容易把主体选错。
- 你先告诉我用途场景，我再继续帮你拆条件和生成候选 SpEL。

理想点说明：
- 没有抢着“瞎写一个”
- 先追问最上游、最关键的问题：场景

==================================================
八、如何使用这些理想回答示例
==================================================

理想回答示例的用途不是要求 skill 一字不差照抄，而是用于检查以下几点：

1. 回答结构是否完整
2. 追问是否问在关键点上
3. 假设是否明确写出
4. SpEL 是否只是“候选表达式”而不是伪装成最终确定答案
5. 解释是否能让工程人员继续往下配置

如果某条测试结果的“表达式”看起来对，但：
- 场景识别错了
- 主体选错了
- 没写假设
- 该追问却没追问
那么仍然不应判高分。

==================================================
十、测试结果反向修订建议
==================================================

如果失败主要集中在某一类问题，可按下面方向修订文档：

1. 经常识别错场景
- 优先补 `references/scene-index.md`
- 补各场景之间的边界信号和易混淆点

2. 经常不会追问
- 优先补 `references/ambiguity-handling.md`
- 把“必须追问”的典型语句写得更明确

3. 经常乱选主体
- 优先补 `references/spel-subjects.md`
- 增加“什么情况下优先考虑哪个主体”的对照说明

4. 经常乱写字段
- 优先补 `references/spel-fields.md`
- 增加“业务词 -> 候选字段”的对应项

5. 输出太像随手回答，不像工程可用结果
- 优先补 `references/spel-examples.md`
- 增加更多“结构化输出范式示例”

6. 主 skill 总是漏掉关键要求
- 回补 `SKILL.md`
- 尤其是 Core Principles、Common Mistakes、Example、Reference Index 部分

==================================================
