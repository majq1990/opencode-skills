Egova SpEL 技能验证用——真实工程师口语测试样例集

说明：
1. 本文件用于验证 egova-eurbanpro-spel-generator skill 是否能正确识别业务场景、拆解条件、识别歧义、进行追问，或在合适时带假设生成候选 SpEL。
2. 样例尽量模拟真实工程人员在配置过程中的自然说法，而非教科书式表述。
3. 每条样例均包含：编号、场景类别、用户口语输入、期望处理方式、验证重点。
4. “期望处理方式”分为三类：
   - 直接生成：信息相对充分，可直接给出候选表达式
   - 先追问：关键信息缺失，不应直接编造表达式
   - 带假设生成：主干信息明确，但字段口径/取值口径未完全确认，应先声明假设再生成

==================================================
一、菜单场景样例
==================================================

[MENU-01]
场景类别：菜单
用户口语输入：
这个菜单只给投诉来源的案件显示。
期望处理方式：带假设生成
验证重点：
- 能识别为“菜单显示/可见性控制”场景
- 能提取“问题来源 = 投诉”
- 能提示“投诉”可能是名称，也可能是来源编码

[MENU-02]
场景类别：菜单
用户口语输入：
我想配个菜单过滤，只有投诉并且现在在核实状态的时候才让它出来。
期望处理方式：带假设生成
验证重点：
- 能识别两个条件需要同时成立
- 能识别“投诉”与“核实状态”分别可能映射到 #bizEntry 和 #state
- 能提醒核实状态实际值域需确认

[MENU-03]
场景类别：菜单
用户口语输入：
这个按钮只有监督中心的人能看见。
期望处理方式：带假设生成
验证重点：
- 能识别这是用户条件驱动的菜单/按钮可见性场景
- 能考虑 #userDetails
- 能提示按部门名称还是按部门 ID 比较需要确认

[MENU-04]
场景类别：菜单
用户口语输入：
投诉案件而且当前处理人是樊考的时候，才显示这个入口。
期望处理方式：带假设生成
验证重点：
- 能拆成案件条件 + 当前用户/办理人条件
- 能区分 #username、#userDetails、#actInst?.humanName 的适用差异
- 不应直接武断认定主体，需说明理解依据

[MENU-05]
场景类别：菜单
用户口语输入：
这个功能不要给受理阶段的案件显示。
期望处理方式：先追问
验证重点：
- 能识别存在“取反逻辑”
- 能追问“受理阶段”到底是状态还是流程节点
- 不应在阶段含义不清时直接输出 != 表达式

[MENU-06]
场景类别：菜单
用户口语输入：
领导说某些特殊案件不要出现这个菜单，你帮我写下。
期望处理方式：先追问
验证重点：
- 能识别“特殊案件”无法直接映射到字段
- 应追问特殊案件对应什么字段或规则
- 不应凭空创造字段名

[MENU-07]
场景类别：菜单
用户口语输入：
我这边想让案件类上报的单子，并且当前登录人是樊考时，菜单可见。
期望处理方式：直接生成
验证重点：
- 能识别 recType 与 username 组合条件
- 能输出结构化说明而不只是扔表达式

[MENU-08]
场景类别：菜单
用户口语输入：
来源是投诉或者举报，满足一个就显示这个菜单。
期望处理方式：带假设生成
验证重点：
- 能识别“任一满足”逻辑，应使用 ||
- 能提醒投诉/举报的值域是否为编码或名称

二、流程引擎自动批转场景样例
==================================================

[FLOW-01]
场景类别：流程引擎自动批转
用户口语输入：
投诉来源的案件自动批转。
期望处理方式：带假设生成
验证重点：
- 能识别为自动批转场景，而不是菜单场景
- 能提取“问题来源 = 投诉”
- 能说明表达式只负责命中条件，不直接说明流向节点

[FLOW-02]
场景类别：流程引擎自动批转
用户口语输入：
如果是投诉，而且当前不在人工审核节点，就走自动流转。
期望处理方式：带假设生成
验证重点：
- 能拆出等值条件 + 排除节点条件
- 能识别流程节点通常优先看 #actInst
- 能说明人工审核节点编码需按项目实际值替换

[FLOW-03]
场景类别：流程引擎自动批转
用户口语输入：
现在只想在受理环节的时候允许它自动往下走。
期望处理方式：先追问
验证重点：
- 能追问“受理环节”是节点名称还是节点编码
- 若项目中也可能用状态表达阶段，应提醒不要混淆

[FLOW-04]
场景类别：流程引擎自动批转
用户口语输入：
到核查这一步，而且当前办理人是张三的时候，走指定分支。
期望处理方式：带假设生成
验证重点：
- 能识别流程条件 + 办理人条件
- 能考虑 #actInst?.actDefName / #actInst?.humanName

[FLOW-05]
场景类别：流程引擎自动批转
用户口语输入：
满足条件的案子直接往下批。
期望处理方式：先追问
验证重点：
- 能识别场景虽然像自动批转，但“满足条件”毫无字段信息
- 应追问具体条件内容

[FLOW-06]
场景类别：流程引擎自动批转
用户口语输入：
核实通过的就自动到下个节点，不通过的别动。
期望处理方式：带假设生成
验证重点：
- 能识别“核实通过”大概率对应状态值
- 能说明“不通过的别动”属于规则含义，不一定都写进表达式
- 若状态值不明，应注明假设

[FLOW-07]
场景类别：流程引擎自动批转
用户口语输入：
这个流程别在某个阶段乱跳，只有街道上报的才自动转。
期望处理方式：先追问
验证重点：
- “某个阶段”不明确
- “街道上报”可能是来源、区域、渠道等，需追问具体字段口径

期望处理方式：带假设生成
验证重点：
- 能识别为“样式命中条件”场景
- 能区分“标红”是效果，不是 SpEL 条件本身

[STYLE-02]
场景类别：案件显示样式
用户口语输入：
待核实的单子高亮一下。
期望处理方式：带假设生成
验证重点：
- 能识别状态条件
- 能映射到 #state 相关字段
- 能提醒待核实的实际状态值要确认

[STYLE-03]
场景类别：案件显示样式
用户口语输入：
投诉来源并且还在受理阶段的，用特殊颜色显示。
期望处理方式：先追问或带假设生成
验证重点：
- 能识别“受理阶段”存在状态/节点歧义
- 如果选择先给候选表达式，必须明确假设是按状态还是按节点理解

[STYLE-04]

[STYLE-06]

[STYLE-07]

- 能考虑 #actInst?.actDefId / #actInst?.actDefName

四、消息配置 / 规则配置场景样例
==================================================

[MSG-01]
场景类别：消息配置 / 规则配置
用户口语输入：
投诉来源的案件触发提醒消息。
期望处理方式：带假设生成
验证重点：
- 能识别为消息/规则触发条件，而非菜单场景
- 能说明表达式负责“是否命中提醒条件”

[MSG-02]
场景类别：消息配置 / 规则配置
用户口语输入：
投诉来源并且核实状态下的时候给我发提醒。
期望处理方式：先追问或带假设生成
验证重点：
- “核实状态下”过于模糊，需确认具体状态值
- 若生成，必须明确假设值

[MSG-03]
场景类别：消息配置 / 规则配置
用户口语输入：
当前流转到人工审核节点就命中这条规则。
期望处理方式：带假设生成
验证重点：
- 能识别节点触发型规则
- 能优先考虑 #actInst

[MSG-04]
场景类别：消息配置 / 规则配置
用户口语输入：
超时还没处理的就发通知。
期望处理方式：带假设生成
验证重点：
- 能识别时间条件 + 未处理状态条件
- 能指出“未处理”字段未必统一，可能需要项目口径确认

[MSG-05]
场景类别：消息配置 / 规则配置
用户口语输入：
投诉案件给监督中心的人发消息。
期望处理方式：先追问
验证重点：
- 能拆分“触发条件”和“接收人配置”
- 不应把“发给谁”直接混写进 SpEL 触发条件里

[MSG-06]
场景类别：消息配置 / 规则配置
用户口语输入：
到了那个阶段的时候提醒我一下。
期望处理方式：先追问
验证重点：
- “那个阶段”完全不明确
- 应追问具体阶段名称/编码，以及它是状态还是节点

[MSG-07]
场景类别：消息配置 / 规则配置
用户口语输入：
某几个来源的案件到核查环节就触发规则。
期望处理方式：先追问或带假设生成
验证重点：
- “某几个来源”值不明确
- “核查环节”可能需要确认名称还是编码
- 条件逻辑一般为来源集合 + 节点条件

[MIX-01]
场景类别：未明确
用户口语输入：
帮我写个只有符合条件才生效的 SpEL。
期望处理方式：先追问
验证重点：
- 能识别场景完全不明确
- 应先问用于菜单、流程、样式还是消息规则

[MIX-02]
场景类别：未明确
用户口语输入：
问题来源是投诉，到了受理阶段的时候用一下这个条件。
期望处理方式：先追问
验证重点：
- 场景未说明
- “受理阶段”语义也不明确
- 不能直接默认成某个场景输出

[MIX-03]
场景类别：未明确
用户口语输入：
特殊人员处理特殊案件时走特殊逻辑。
期望处理方式：先追问
验证重点：
- 主体、字段、场景都不清晰
- 应追问“特殊人员”“特殊案件”“特殊逻辑”分别指什么

[MIX-04]
场景类别：未明确
用户口语输入：
这个条件我想限制一下，不满足就别显示。
期望处理方式：先追问
验证重点：
- 有显示语义，可能偏菜单或样式，但仍不够明确
- 应追问显示对象是什么，以及判断条件是什么

[MIX-05]
场景类别：未明确
用户口语输入：
你先按常见写法帮我出一个，后面我再去对值。
期望处理方式：带假设生成
验证重点：
- 当用户明确接受“先按常见写法”，skill 可以带假设生成
- 但必须把假设写清楚，不能包装成最终答案

==================================================
六、建议验证维度
==================================================

可用本样例集从以下几个角度检查 skill 质量：

1. 场景识别是否稳定
- 菜单
- 流程引擎自动批转
- 案件显示样式
- 消息配置 / 规则配置
- 场景不明确时是否会先追问

2. 条件拆解是否正确
- 是否能从口语中拆出来源、状态、节点、用户、时间等条件
- 是否能判断是同时满足还是任一满足
- 是否能识别排除条件和取反逻辑

3. 主体/字段映射是否克制
- 是否优先使用已有主体：#bizEntry、#state、#actInst、#timing、#userDetails、#username
- 是否避免把中文业务词直接写成字段名
- 是否避免臆造新主体、新字段

4. 歧义处理是否合理
- 关键歧义是否先追问
- 非关键歧义是否明确假设后再生成
- 是否能区分“命中条件”和“效果/接收人/动作本身”

5. 输出结构是否像工程可用结果
- 是否包含场景识别
- 是否包含条件提取
- 是否包含主体 / 字段映射
- 是否包含追问项或假设项
- 是否包含候选 SpEL
- 是否包含中文说明

==================================================
七、使用建议
==================================================

建议后续实际验证时，可按以下方式使用本样例集：

- 第一轮：只测场景识别是否正确
- 第二轮：测追问是否问到点子上
- 第三轮：测带假设生成时是否写清假设
- 第四轮：测最终表达式结构是否符合 references 中的输出范式

若某类样例持续失败，可反向补充到：
- references/ambiguity-handling.md
- references/spel-examples.md
- SKILL.md 的 Common Mistakes / Example / Reference Index 部分
