# SpEL 主体说明

> 用于说明麒舰业务中常见 SpEL 主体分别代表什么、适合承载哪类条件，以及生成表达式时应如何选择主体。
> 本文档会尽量区分 **已确认强证据**、**某场景常见**、**尚未确认统一支持** 三种口径，避免把某个子系统里的能力误写成全项目通用能力。

## 总览

根据当前项目资料与已完成的 research，已出现的常见 SpEL 主体包括：

- `#bizEntry`
- `#actInst`
- `#timing`
- `#userDetails`
- `#username`
- `#state`

这些主体并不表示“所有场景都一定支持”，而是当前资料中已经出现、应优先检查的主体来源。

生成表达式时，应先判断业务场景和条件类型，再选择最合适的主体。

---

## 证据口径说明

### 1. 已确认强证据

表示已经看到较明确的代码证据，例如：

- `context.put(...)`
- `setVariable(...)`
- provider 中显式映射主体名
- 同类场景里反复出现、证据较稳定

### 2. 某场景常见 / 可见

表示该主体在部分业务实现里反复出现，但还不足以代表“所有场景统一支持”。

### 3. 尚未确认统一支持

表示已经看到相关业务场景或上下文线索，但 research 还没有确认统一稳定的主体名或注入方式。

---

## 1. `#bizEntry`

### 含义

表示案件 / 业务实体本身，是当前证据最稳定的主体之一。

### 证据等级

- **已确认强证据**
- core 与 mis-core 都有较明确、跨场景的代码证据

### 适合承载的条件

通常用于承载案件本身的业务属性，例如：

- 案件类型
- 问题来源
- 问题分类
- 案件地址
- 区域/街道/社区
- 上报渠道
- 案件描述

### 常见使用方式

```spel
#bizEntry?.recTypeId == 1
#bizEntry?.eventSrcId == 1
#bizEntry?.recTypeId == 1 && #bizEntry?.eventSrcId == 1
```

### 适用判断信号

当需求描述里出现以下词时，通常优先考虑 `#bizEntry`：

- 案件类型
- 问题来源
- 问题类别
- 区域
- 地址
- 案件本身属性

### 注意事项

- 中文业务词不能直接当字段名使用，应结合字段映射表确认
- 名称类值和编码类值要区分清楚
- 即使 `#bizEntry` 很常见，也仍应先确认当前场景是否真的提供了业务实体上下文

---

## 2. `#state`

### 含义

表示案件状态信息。

### 证据等级

- **MIS 范围：已确认强证据**
- **core 范围：尚未确认通用支持**

目前 research 已在 MIS 规则 provider、反馈规则、样式上下文等位置看到较明确的 `#state` 证据；但在 core 中暂未看到足够强的通用注入证据。

### 适合承载的条件

通常用于承载案件当前所处状态、核实/核查/复查等状态标识，例如：

- 核查状态
- 核实状态
- 复查状态
- 派遣状态
- 流程状态
- 重点案卷标识
- 是否自处置
- 部分 MIS 样式相关状态判断

### 常见使用方式

```spel
#state?.verifyMsgStateId == 4
```

### 适用判断信号

当需求描述里出现以下词时，**可优先考虑是否为 `#state` 场景**：

- 当前状态
- 核实状态
- 核查状态
- 派遣状态
- 是否重点案件
- 某个明确状态值

### 注意事项

- “阶段”一词不一定总是 `#state`，有时也可能对应流程节点或流程定义
- 菜单、workflow 等场景里，用户说的“受理阶段”“核查阶段”很可能其实是节点条件，应先和 `#actInst` 区分
- 不能因为 MIS 某些规则链路明确支持 `#state`，就直接把它当成所有 core 场景的默认主体

---

## 3. `#actInst`

### 含义

表示案件流程实例 / 当前活动实例信息，是当前证据最稳定的主体之一。

### 证据等级

- **已确认强证据**
- core workflow / 菜单、mis-core 多类业务场景里都有较明确证据

### 适合承载的条件

通常用于承载流程相关信息，例如：

- 当前活动定义
- 当前节点
- 流程定义
- 上一节点
- 处理人
- 处理岗位
- 流程参与者
- 活动状态

### 常见使用方式

```spel
#actInst?.actDefId != 'artificial_597c44be-382c-462d-ad12-f0ffb7ba7407'
```

### 适用判断信号

当需求描述里出现以下词时，通常优先考虑 `#actInst`：

- 当前节点
- 当前环节
- 流程定义
- 流转到哪一步
- 上一环节
- 办理人 / 处理岗位

### 注意事项

- 用户口中的“阶段”有时其实是流程节点，应注意和 `#state` 区分
- 节点名称、节点编码、`actDefId` 往往不是一回事，需要确认实际值域
- “当前处理人”有时可能来自流程实例，有时也可能是当前登录用户，不要把 `#actInst` 与 `#username` / `#userDetails` 混写

---

## 4. `#timing`

### 含义

通常用于表达时限、计时、剩余时长、超时类信息。

### 证据等级

- **尚未确认统一支持**

当前 research 已看到 core 与 mis-core 中都存在 timing 相关业务场景，但还没有确认统一稳定的 `context.put("timing", ...)` 或等价注入证据。

### 适合承载的条件

如果当前项目明确存在 `#timing` 主体，则它通常适合承载：

- 是否超时
- 剩余时限
- 已用时长
- 截止时间
- 警告时间
- 某时间区间内是否满足条件

### 适用判断信号

当需求描述里出现以下词时，通常应先判断是否属于 timing / 时限类条件：

- 超时
- 临近超时
- 剩余时限
- 已用时长
- 截止时间
- 计时

### 注意事项

- 不能因为项目里存在 timing 模块，就直接把 `#timing` 当作已统一确认支持的主体
- 超时类条件在不同项目中也可能通过其他上下文实现，例如 MIS 样式扩展上下文中的时限相关对象
- 时间条件往往还需要确认比较单位，是小时、时间戳还是具体日期时间

---

## 5. `#userDetails`

### 含义

表示当前登录用户的详细信息。

### 证据等级

- **某场景常见 / 可见**
- core 中有通用补充证据，mis-core 多类业务场景也较常见

### 适合承载的条件

通常用于当前登录用户的属性判断，例如：

- 人员名称
- 部门
- 区域
- 租户
- 账号名称
- 组织属性

### 适用判断信号

当需求描述里出现以下词时，通常优先考虑 `#userDetails`：

- 当前用户所在部门
- 当前用户所属区域
- 某类人员
- 某组织下人员

### 注意事项

- 如果需求只需要比较当前用户名本身，可能直接用 `#username` 更直接
- “角色”“岗位”“组织”是否都在 `#userDetails` 中，需要按字段表确认，不要想当然扩展
- 虽然 `#userDetails` 在多类场景中常见，但仍不应默认所有规则场景都统一提供它

---

## 6. `#username`

### 含义

表示当前用户名称或当前登录用户标识。

### 证据等级

- **某场景常见 / 可见**
- core 菜单与 mis-core 多类业务中有较明确证据，但通用性弱于 `#userDetails`

### 适合承载的条件

通常用于直接比较当前用户名，例如：

- 当前用户是否为某个人
- 某人可见 / 某人触发 / 某人办理时生效

### 常见使用方式

```spel
#bizEntry?.recTypeId == 1 && #username == '樊考'
```

### 适用判断信号

当需求描述里出现以下词时，通常优先考虑 `#username`：

- 当前用户名
- 指定人员名称
- 某个人可见

### 注意事项

- `#username` 更适合“直接比较名称”，如果需要更多用户属性，应考虑 `#userDetails`
- 使用人名比较时，要确认系统实际传入的是中文名、登录名还是其他账号标识
- 如果用户口中的“当前处理人”其实是流程实例中的办理人，而不是当前登录人，则不应直接用 `#username`

---

## 主体选择建议

### 优先按条件类型选主体

- 案件属性 → `#bizEntry`
- 流程节点 / 流程实例 → `#actInst`
- 当前登录用户属性 → `#userDetails`
- 当前登录用户名 → `#username`
- 明确状态值条件 → 先判断是否属于 `#state` 场景
- 时限 / 超时 / 计时 → 先判断当前项目是否真的提供 `#timing`

### 多条件组合时允许跨主体

一个表达式中可以同时出现多个主体。例如：

```spel
#bizEntry?.recTypeId == 1 && #username == '樊考'
```

这类写法适合“案件条件 + 用户条件”同时判断的场景。

### 先确认场景再确认主体

虽然多个场景可能共用同一主体，但仍应先确认当前场景是否支持该主体，再输出最终表达式。

特别要避免：

- 在菜单场景里一看到“阶段”就直接写 `#state`
- 在 workflow 场景里把状态条件和节点条件混成同一类
- 在样式或消息场景里把 `#timing` 写成已无争议确认支持的主体

---

## 常见误区

- 把所有“阶段”都归到 `#state`
- 把所有“用户相关判断”都写成 `#username`
- 把“当前处理人”和“当前登录人”混为一谈
- 看到中文业务词就直接拼字段名
- 不区分名称值和编码值
- 未确认场景支持范围就直接套主体
- 因为 MIS 某个场景支持 `#state`，就把它推广成全项目通用能力
- 因为存在 timing 模块，就把 `#timing` 当成已统一确认主体
