# novel-segment-summary：超长文本分节点总结

## 何时用

**用**：输入是单次上下文装不下的长文本，且用户要**全量**覆盖 + **分层**产出。

- 经验阈值：> 20 万字符就该用本流程；> 100 万字符必须用（单 agent 读不完）。
- 典型输入：完本网络小说（100–700 章，100–500 万字）、多篇合订报告、多年日志合集。
- 典型诉求："读完整本，按 50 章一个节点，总结故事流程和主要冲突、成就"。

**不用**：几万字以内的单篇文档（直接 Read）；只要定位/检索（用 grep / 搜索）；只要某一章（直接读该行区间）。

## 核心思路：地图-归约（map-reduce）

整本书 400 万字符 ≈ 400 万 token，任何单次上下文都装不下，所以必须两层分解：

```
原文（N 万行）
  └─ 节点（用户要的总结粒度，默认 50 章）
       └─ 阅读块（单 agent 一次能吃下的量，默认 ≤7000 行 / ≈10 万字符）
            └─ 子 agent 逐块读 → 块总结（落盘 + 返回）
                 └─ 主 agent 归约 → 节点总结（故事流程 / 主要冲突 / 成就）
```

**分工原则**：子 agent 只负责"读懂并压缩"（局部、可并行、无状态）；主 agent 只负责"归约与交付"（全局、需要判断力）。主 agent **绝不**自己去读原文正文——那是 400 万 token，读了就废。

## 五步工作流

### Step 0 · 准备交付目录

产物按全局规范落到当天日期目录：

```bash
mkdir -p "D:/opencode/file/<yyyy-mm-dd>/<书名>-总结/chunks"
```

### Step 1 · 侦察（不可跳过）

```bash
# 体量
wc -l -m "<文件>"

# 章节标题格式与分布（先 head 看几条，确认正则）
grep -n -E "^\s*第[0-9]+[章节卷]" "<文件>" | head -40
```

关键点：**不要用"平均章节长度"推算行号**。章节长度差异可能到 3 倍，必须按实际标题行号定位。

### Step 2 · 生成分块计划（用脚本，别手算）

```bash
python3 <skill>/scripts/plan_chunks.py "<文件>" \
  --node-size 50 --max-lines 7000 \
  --out "D:/opencode/file/<yyyy-mm-dd>/<书名>-总结/分块计划.md"
```

脚本会输出：节点表、块表、**覆盖率自检**（块区间首尾相接/无重叠/无遗漏）、**原文数据质量告警**（章节跳号、重复标题、异常短区间＝疑似乱码插入）。

先把告警读完再派发——这些结论要写进子 agent 的 prompt。

### Step 3 · 并行派发子 agent

- 子 agent 类型：`general-purpose`（需要 Read + Write）。
- **每批 8 个**，同一条消息里并发调用（一批太多容易撞服务商限流）。
- 每个子 agent 用同一份模板，只替换「行区间」和「本块覆盖章节」：见 `references/agent-prompt-template.md`。
- 模板里**必须**包含的三条硬指令：① 先写文件再返回全文；② 忽略乱码/无关段落；③ 章节跳号属正常。

### Step 4 · 收尾检查 + 补齐

限流/超时会让个别 agent 失败。**不要凭 agent 的返回消息判断成败——去查磁盘**：

```bash
ls "<交付目录>/chunks/" | sort          # 看哪些块文件存在
for f in "<交付目录>/chunks/"*.md; do echo "$(basename $f): $(wc -c < $f)"; done
```

已落盘且长度正常的块＝成功（哪怕它的最终返回消息被限流截断）。只重跑**真正缺失或过短**的块，其余不要重跑（省时省钱）。

### Step 5 · 归约 + 交付

主 agent 把各块总结（从上下文里的返回，或直接 Read 落盘文件）归约成节点级总结：

- 每个节点固定三段：**【故事流程】/【主要冲突】/【成就与收获】**，末尾可加【关键人物】【遗留伏笔】。
- 节点开头给一句"这个节点讲什么、处在什么阶段"，让读者能跳读。
- 保留专有名词与数字（比分、纪录、技能名、任务名、奖项）——它们是长文总结的价值所在。
- 最后补：全书基本信息、一句话主线、贯穿全书的暗线、结局一览表、数据质量备注。

交付物：

```
D:/opencode/file/<yyyy-mm-dd>/<书名>-总结/
  ├── 分节点总结.md        ← 主交付物（节点级三段式总结）
  ├── 分块计划.md          ← 分块表与覆盖率自检
  └── chunks/块NN.md       ← 块级明细，可追溯、可复算
```

## 硬规则（血泪清单）

1. **子 agent 必须"先写文件，再返回全文"**。这是抗限流的核心设计：agent 的最终返回可能被服务商限流截断，但文件已经落盘，主 agent 能无损恢复。少了这条，限流＝这块工作全丢。
2. **判断成败看磁盘，不看返回消息**。本流程实测出现过 3/48 个 agent 返回 `Provider rate limited`，但其中 2 个的块文件已完整落盘——只有 1 个真的需要重跑。
3. **块大小按"行数"而不是"章数"切**。章节长度不均，按章切会出现某块 20 万字符（读不完）而另一块 2 万字符（浪费）。默认 ≤7000 行 ≈ 10 万字符。
4. **必须显式告知子 agent 忽略三类噪声**：① 章节跳号（作者重排）；② 混入的其他作品/乱码段落；③ 文件末尾的作者新书宣传与导流。不告知，agent 会把噪声写进总结。
5. **不要抽查代替全读**。用户要"读完整个小说"，就必须让每个块都被真实读过。跳块会让节点总结出现空洞，且主 agent 无法察觉。
6. **主 agent 不要亲自读正文**。一旦读了原文，上下文立刻爆掉，归约阶段的判断力也没了。
7. **不要用 `TaskOutput` 之外的轮询等 agent**。派发后继续做别的事（例如写 Step 0 的目录、整理上一个节点的归约），agent 完成会自动通知。
8. **产物路径守规范**：一律 `D:\opencode\file\<yyyy-mm-dd>\`，不要落在 `D:\opencode` 根目录。

## 参数经验值

| 参数 | 默认 | 依据 |
| --- | --- | --- |
| 节点章数 | 50 | 用户诉求；也是"一段完整剧情弧"的常见长度 |
| 单块行数上限 | 7000 | ≈10 万字符；中文 1 字符 ≈ 1 token，200K 上下文 agent 的安全区 |
| 每批并发 agent | 8 | 再高容易触发服务商限流 |
| 子 agent 单次 Read | 2000 行 | Read 工具默认上限，需分段多次读 |
| 节点总结长度 | 800–1500 字 | 低于 500 字丢信息，高于 2500 字读者不看 |

## 自检清单（交付前逐条过）

- [ ] 分块计划的覆盖率自检为 ✓（首块从第 1 行起、末块到文件尾、块间无缺口无重叠）
- [ ] `chunks/` 下的块文件数量与计划一致，且每个都非空
- [ ] 每个块文件都覆盖了它的完整行区间（抽查开头结尾）
- [ ] 节点数 = ceil(章节数 / 节点章数)，且每个节点都有三段式总结
- [ ] 原文数据质量告警已写进最终交付物的「备注」段
- [ ] 交付物路径符合 `D:\opencode\file\<yyyy-mm-dd>\` 规范
- [ ] 没有把原文噪声（乱码/其他作品/宣传）写进任何一层总结

## 附件

- `scripts/plan_chunks.py` —— 分块计划生成器（节点表 + 块表 + 覆盖率自检 + 数据质量告警）
