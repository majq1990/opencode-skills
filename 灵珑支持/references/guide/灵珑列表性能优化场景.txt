灵珑列表性能优化场景
一、核心问题
灵珑列表是基于视图制作的，视图配置sql效率决定了灵珑列表性能表现。与硬编码不同，灵珑的sql是通过配置手段按一定规则来生成的，其核心解决以下问题：
如何通过低代码方式优化sql索引策略
如何通过低代码方式sql查询策略优化

基于会话变量性能优化场景

基于导航属性性能优化场景
背景描述
临沂广告系统面向市民公众号服务中的备案记录一栏页面打开极慢，工程反馈需要半分钟。能否打开全凭运气，极大影响用户使用。
配置SQL
select 
ad.approval_id,
ad.documentNo,
ad.remark,
ad.check_result,
case check_result when 1 then '服务中' when 2 then '服务完成' when 3 then '退回' when 4 then '作废' else '待提交' end as checkResult,
ad.advert_status_id,
ad.advert_status_name,
ad.advert_name,
ad.create_time,
ad.set_location,
ad.evaluate_flag,
ad.safe_check_state,
ad.applicant_unit,
ad.setter_person,
wf.taskId,
wf.nodeName,
service.documentNo as serviceNo
 from advert_record ad
left join 
( SELECT
  _main.ID_ taskId,
_main.CREATE_TIME_ createTime,
_main.NAME_ nodeName,
record.documentNo documentNo
FROM
act_ru_task _main
INNER JOIN lcwf_process_record record ON _main.PROC_INST_ID_ = record.processInstanceId 
WHERE
_main.ASSIGNEE_ IS NULL 
ORDER BY
_main.CREATE_TIME_ DESC) wf 
on ad.documentNo = wf.documentNo
left join 
advert_service_evaluation service
on ad.documentNo = service.approval_no
where ad.advert_type_id = 2 and ad.valid_flag = 1 
group by ad.approval_id
order by ad.approval_id desc
原因分析
经上述分析，页面无法正常打开其核心问题是SQL性能较差，advert_record与act_ru_task两张表记录较多，大表之间关联查询致使SQL速度慢。
如何优化
在列表或详情部件采用查询关联表的字段来展示数据信息的场景，可以使用数据视图的“导航属性”两次查询特性来解决大表关联查询带回的性能问题，操作如下：
添加导航属性“任务信息”，配置关联关系
在列表的数据面板“隐藏字段”栏点击添加来增加计算字段，把任务信息里面的taskId和nodeName字段进行拆解。如下图：
配置内容：ARRAY_FIRST('#{tasks.taskId}')
因为之前的列表会使用到taskId来进行参数传参，所以才需要通过这种方式把之前的字段取出
优化成果
优化之前 （响应时间>5.4S）
优化之后（响应时间<3S）
知识总结
导航属性是根据配置的关联关系在查询数据之后再进行二次查询，本质是采用分步查询方案来替换大表关联查询引起的性能问题。
可以使用公式来拆解导航属性，把导航属性打平使其保持与原有结构一样。
