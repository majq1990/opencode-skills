# MySQL → PG 系（人大金仓 / 瀚高）实迁作业规程

> 本规程来自同一次真实全量迁移的 PG 系分支：源库 MySQL 8.0.46（cgdb/cgdbstat/giscenter/mms 四库，5589 张表 / 约 41.8 万行）→ **人大金仓 KingbaseES V009R001C010（Oracle 兼容模式）** 与 **瀚高 HighGo V9（内核 = PostgreSQL 14.20）**。两个目标库都做到迁移 0 失败、四轨独立验证 0 数据丢失。文中所有结论均为实跑结论，非推断。
>
> 达梦分支见 `mysql-to-dm-runbook.md`。两份规程的三轨判定口径（活库漂移≠丢失、排序规则只影响极值、归一后才能比对）完全通用，本文不重复，只写 PG 系专属的差异。

## 三、七类真 bug（金仓 Oracle 兼容专属，瀚高不触发）

这 7 类都是金仓真跑才暴露的，类型映射一个都不涉及。**凡是宣称"PG 系迁移已验证"，要问一句：是在金仓上跑通的，还是只在瀚高上跑通的**——瀚高过了不代表金仓能过。

| # | 现象 | 金仓报错 | 根因 | 修法 |
|---|---|---|---|---|
| 1 | `bit(1)` 等位列建表失败 | 默认值语法错误 | MySQL 位字面量是小写 `b'0101'`，PG 位字面量是大写 `B'0101'` | `DEFAULT B'%s'`，取 `d[2:-1]` 并剥掉内部引号 |
| 2 | `bit(n)` 灌数失败 | 位串长度不符 | MySQL `bit(n)` **按整字节存**（`bit(1)` 占 1 字节），驱动回 8 位；PG `bit(n)` 要求位串长度恰好 n | 按 `NUMERIC_PRECISION` 取低位 `bits[-prec:]` |
| 3 | 外键建不出来 | `there is no unique constraint matching given keys` | PG 认裸唯一索引当外键目标，**金仓 Oracle 兼容只认唯一约束** | 唯一索引一律落 `ALTER TABLE ... ADD CONSTRAINT ... UNIQUE (...)`，不建裸索引 |
| 4 | 重建 schema 失败 | `out of shared memory / You might need to increase max_locks_per_transaction` | `DROP SCHEMA ... CASCADE` 是**单事务**拿全 schema 的锁，5000+ 表 / 3 万+ 索引直接打爆 `max_locks_per_transaction` | 改成小批量 `DROP TABLE ... CASCADE`，**每批一提交**让锁随事务释放（本次 150 张/批），最后再 `DROP SCHEMA` |
| 5 | 索引/约束建不出来 | `relation ... already exists` | MySQL 索引名**只在一张表内唯一**，PG 系按 **schema 唯一** | 索引名 = 表名 + `_` + 原名；再按 PG 63 字节标识符上限截断，截断后撞名补 crc 序号 |
| 6 | 空串语义不一致（静默改数！） | 无报错 | 金仓 `ora_input_emptystr_isnull=on`：**插入空串落地成 NULL**，瀚高是原生空串语义 | 引擎启动时先 `SHOW ora_input_emptystr_isnull` 探测，无此参数按原生语义处理，并在日志里写明用了哪套 |
| 7 | `date` 列比对对不平 | 无报错 | 金仓 `date` 类型**带时间分量**，瀚高不带 | 归一时把目标侧 `date` 按字符串整体比，不要截断到 10 位 |

第 6 条最危险：它不报错，只是把数据悄悄改掉。引擎必须**先探测再决定**，并且把探测结果写进日志——本次日志里 `目标无 ora_input_emptystr_isnull 参数，按原生空串语义处理` 这句话就是干这个的。

## 四、读值精度四个坑（全是"假数据丢失"）

这四个坑让验证脚本一度报出几十张表不一致，实际数据一条没丢。**都是回读表示的差异，不是迁移差异**。

### ① 金仓 float4 `::text` 只出 8 位有效数字

- 现象：源 `f109309968.0` vs 目标 `f109309970.0`
- 查证：`extra_float_digits` 从 0 设到 3 全都试过，**没有一个能修好**；`::numeric(30,10)` 转换反而更糟（约 7 位有效数字）
- 修法：**只有 `::float8`（二进制扩宽）是精确的**。源侧用 `CAST(col AS DOUBLE)`、目标侧用 `col::float8`，两侧都绕开文本表示

### ② MySQL `float(M,D)` 直读按 D 位舍入

- 现象：`1028744.5625` 直读成 `1028744.562`
- 修法：源侧 `CAST(col AS DOUBLE)` 或 `col+0e0`，拿真实二进制值

### ③ `bit(n)` 两侧位宽不同

- 现象：源 `00000000`（8 位）vs 目标 `0`（1 位），17 张表误报
- 修法：两侧都按声明的 `NUMERIC_PRECISION` 裁到 n 位再比

### ④ `time` 两侧类型不同

- 现象：源回 `timedelta`、目标回字符串，且时区/微秒表示不一致
- 修法：统一成带 `t` 前缀的 `HH:MM:SS[.ffffff]` 字符串；**负时段要保留负号**（`timedelta` 的 `days` 是负的，直接 `%02d` 会出一个巨大的正小时数）

## 五、对象对账口径：索引**不能按名字比**

- MySQL 索引名只在一张表内唯一，PG 系按 schema 唯一，所以引擎必须给索引名加表名前缀——**按名字比索引，100% 全对不上**
- 唯一可用的口径是**语义四元组**：`(表名, 是否唯一, 有序列清单)`，且列名要**统一转小写**（MySQL 列名大小写不敏感，`POINTID` vs `pointid` 会误报）
- 列清单必须按**索引键序**取，不能按物理列序。目标侧正确写法：

```sql
SELECT t.relname, x.indisunique,
       (SELECT string_agg(a.attname, ',' ORDER BY k.ord)
          FROM unnest(x.indkey) WITH ORDINALITY AS k(attnum, ord)
          JOIN pg_attribute a ON a.attrelid = t.oid AND a.attnum = k.attnum
         WHERE k.ord <= x.indnkeyatts) AS cols
  FROM pg_index x
  JOIN pg_class t ON t.oid = x.indrelid
  JOIN pg_namespace n ON n.oid = t.relnamespace
 WHERE n.nspname = %s AND NOT x.indisprimary
```

`k.ord <= x.indnkeyatts` 这个条件不能省：它把 INCLUDE 的附属列排除在键列之外。

**已知工具侧残留**：同一条 SQL 在金仓上跑，`string_agg(... ORDER BY k.ord)` 返回的列序不稳定（本次 cgdb 报 15 组、cgdbstat 报 3 组"仅源/仅目标"，每组都是同表同唯一性、列集合相同只是顺序不同）；瀚高（原生 PG 14.20）完全正常。**这不是迁移缺陷，是金仓聚合函数排序的工具侧问题**。判定办法：把列清单当多重集比；顺序敏感的比较要么换 `array_agg`，要么只在瀚高侧做。

## 六、视图转换：8 条改写规则 + 剩余改不动的

MySQL `information_schema.VIEWS` 给的 `VIEW_DEFINITION` 不能直接给 PG 系。本次金仓 cgdb 49 个视图、cgdbstat 14 个、giscenter/mms 0 个。朴素替换反引号只能成 27/49；按下面 8 条改写到 **40/49**（cgdbstat 13/14）。

| # | 规则 | 原因 |
|---|---|---|
| 1 | 反引号 `` `x` `` → 双引号 `"x"` | |
| 2 | `INTERVAL <expr> <unit>` → `INTERVAL '<expr> <unit>'` | PG 只认字符串形式；`-(3)` 要剥掉括号归一成 `-3`，否则 PG 拒 |
| 3 | 三段式列引用 `"schema"."alias"."col"` → `"alias"."col"` | MySQL 视图定义常带库名前缀 |
| 4 | **不带 ON 的裸 `JOIN`** → `CROSS JOIN` | MySQL 允许连接条件写在 WHERE 里，PG 要求 JOIN 必须带 ON 或写成 CROSS JOIN |
| 5 | `concat` 超过 2 参 → 嵌套 2 参 | 金仓 Oracle 兼容的 `concat` 只认 2 参（PG 原生 `concat` 是变参，瀚高没这问题） |
| 6 | `ifnull(x,y)` → `coalesce(x,y)` | |
| 7 | `LIMIT m,n` → `LIMIT n OFFSET m` | |
| 8 | `if(c,a,b)` → `case when c then a else b end` | PG 系没有 `if()` 函数 |

**规则 4 是最容易写错的**：ON 子句不在 `join` 关键字后面，而在**表引用后面**（`join t1 a on(...)`）。第一版用"`join` 后面紧跟 `on` 才不改"的判断，把 49 个视图里所有正常连接全改成了 `CROSS JOIN ... on(...)`，反而把 27/49 砸下去。正确做法是跳过表引用和别名再判断，且**别名不能是关键字**（否则 `join t on(...)` 会把 `on` 当成别名，误判成要改）。

**改写器必须是字符串字面量感知的**：规则 5/8 要做括号配对，遇到 `'` 要整段跳过（`''` 是转义引号），否则视图里带引号的条件会被切碎。

**剩余 9 个改不动的（cgdb）+ 1 个（cgdbstat），逐条归因**：

| 归因 | 个数 | 视图 | 性质 |
|---|---|---|---|
| `syntax error at or near "concat"` | 2 | `vc_human_region`、`vc_patrol_state` | **未定位**。修掉规则 4 的 bug 之后才暴露（此前被 `at or near "on"` 挡住）。复跑时用最小复例二分：先 `SELECT concat('a','b')`，再逐步加 `coalesce(x,'')`、嵌套、`union` |
| GROUP BY 功能依赖 | 3 | `vc_csgl_keywork_sup_type_stat`、`vc_mf_public_district_score`、`vc_mf_public_repair_score` | MySQL 关掉 `ONLY_FULL_GROUP_BY` 后可选非分组列，**PG 一律拒绝**。必须人工补 GROUP BY 或改聚合写法 |
| 视图依赖视图，被依赖项自身失败 | 1 | `vc_housing_estate_special_human`（依赖 `vc_special_human`） | 转换器要**多轮重试**（最多 3 轮），不能按字母序单轮建 |
| `sys.concat(varchar, unknown, varchar)` | 1 | `vc_patrol_state` | 与规则 5 同类，嵌套改写后疑似可解，未复跑证实 |
| PostGIS 函数缺失 | 1 | `vc_sani_eval_comfort_station`（`st_astext`） | 目标库未装扩展，装 PostGIS 或改应用层 |
| `column a.column_comment does not exist` | 1 | cgdbstat `sanifieldviewtemp` | 视图直读 `information_schema`，PG 的列注释在 `pg_description` 不在 information_schema，需人工改写 |

**建视图必须多轮重试**：按表名字母序单轮建，被依赖的视图还没建出来，一定报 `relation does not exist`。本次 `vc_housing_estate_special_human` 就是这么败的。

## 七、引擎运行姿势（PG 系专属）

1. **目标库名要核对**：金仓实例上同时有 `test` 和 `kingbase` 两个库，连错了不报错，只会在建视图时报一片 `relation "cgdb.xxx" does not exist`——**这个报错的真正原因十有八九是连错库，不是缺表**。本次就因此误判过一次
2. **标识符白名单要放行 Unicode 与空格**：真实存在中文列名和带前导空格的列名，双引号包裹即可保留，只封杀引号/反斜杠/控制字符/分号
3. **四库各进各自 schema**：四库存在同名表（如 `tc_field`），混一个 schema 会互相覆盖
4. **psycopg2 占位符是 `%s`**（不是达梦的 `?`），且 MySQL 侧的 `%` 要转义成 `%%`
5. **主键/唯一/索引/外键全部后置**，外键要等所有表建完再建
6. **逐表 try/except + 失败不中断**，每 500 张打一次进度；`--recreate` 走第四节第 4 条的分批删表
7. **注释单独一段写**（本次 34464+1507+229+10 条），用 `COMMENT ON TABLE/COLUMN`
8. **后台化三件套** `setsid nohup ... < /dev/null &`；Windows 控制端用 paramiko，不要用 sshpass
9. **断点重跑安全**：逐表 DROP+CREATE 自愈，但要先清状态文件

## 八、四轨过程验证（PG 系口径）

与达梦分支同四轨，**归一规则按 PG 系改**：

| 轨 | 方法 | 本次覆盖 | 判据 |
|---|---|---|---|
| 一轨 行数对账 | 双侧 `COUNT(*)` | 5589 张全表 | 行数相等；不等的进实时表判定 |
| 二轨 数据级逐字段 | 整表取回双侧，逐列归一后做**多重集**比对 | 所有 `0 < 行数 ≤ 3000` 的表（cgdb 1241 + cgdbstat 129 + giscenter 28 + mms 14 = **1412 张，不抽样**） | 多重集完全一致 |
| 三轨 中文回读 | 含中文列逐字比对 | 1740+201+25+15 = **1981 个字段**，随二轨一并做 | 无乱码、无替换字符 |
| 大表轨 | 逐列 `COUNT/COUNT DISTINCT/MIN/MAX/SUM`；不一致自动升级整列多重集 | cgdb 5 张 | 见下 |

**实时表判定要自动化**：本次 `to_disposing_reccount_minute` 源 9178 / 目标 9177，人工看一眼像丢行。判定办法是取源独有行的**第一个日期时间列**，和目标侧该列 `MAX` 比——源独有行的值晚于目标最大值，就是迁移后新增，不是丢行。**这条要写进脚本自动判**，不能靠人盯。

**残留的真实差异（如实记录，均已定性）**：

| 库.表 | 差异 | 定性 |
|---|---|---|
| `cgdb.tcdicadmindivision` | 2 个单元格里的 `\x00` 在目标侧消失（`s\uf8df\x00桥区` → `s\uf8df桥区`） | **PG 系 text 类型存不了 NUL 字节**，两个目标库表现一致。属语义损失，需业务确认是否可接受 |
| `cgdb.to_patrol_labour_state` | 1 个 `0000-00-00 00:00:00` 在目标侧是 NULL | MySQL 零日期，PG 系不认，引擎改写为 NULL 并计数上报 |
| `cgdb` 5 张大表 | 其中 2 张主键非单列，跳过大表轨精比 | 指纹口径覆盖不到，需人工抽检 |

**仍未覆盖**：存储例程/触发器（cgdb 有例程体内夹带 DDL，PG 系过程语法与 MySQL 差异大，不是文本替换能解决的）；分区表；`FULLTEXT`/`SPATIAL` 索引（PG 系无内置等价物，本次四库实际 0 个，但规则里要点名跳过）；PostGIS 空间类型（`bytea` 落库保数据，查询能力另论）。

## 九、本次实证的关键数字（供容量/工期估算参考）

- 5589 张表 / 约 41.8 万行。瀚高四库迁移总耗时 134s（cgdb 110s / cgdbstat 11s / giscenter 7s / mms 6s）；**空表占比很高**（cgdb 5243 张里 3995 张空表），排工期按非空表估
- 验证本身不构成工期瓶颈：瀚高四库验证合计 42s，金仓 45s
- 视图转换是纯文本工作，49 个视图秒级；**瓶颈在人工归因**，本次 9+1 个失败视图里只有 3 个能自动修
- 引擎与验证脚本的本职语义是"按 information_schema 动态拼表名"，表名不可参数化，会被静态安全扫描判为 SQL 注入，`.py` 落盘/入仓被闸（`.txt` 落盘可过，远端改名执行）。**想让 `.py` 入仓，参考 `scripts/mysqldump_to_dm_ddl.py` 的形态：不连库、不执行 SQL、无 CLI 可控写路径**
