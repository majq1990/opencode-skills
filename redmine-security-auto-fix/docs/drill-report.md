## 二、演练过程与三次状态

同一个附件、同一条命令，前后跑了三次，结果完全不同——这三次就是本次演练最有价值的产出。

| 轮次 | 代码版本 | 结果 | 问题 |
|---|---|---|---|
| 第一轮 | v2.5.0 通用解析 | **363 条垃圾记录** | 卡片里的报告标题、HTTP 方法和路径被当成漏洞；等级全是"中危" |
| 第二轮 | v2.6.0 收紧后 | **0 条** | 方向对了，但把真实漏洞一起关在门外 |
| 第三轮 | v2.7.0 专项解析器 | **52 条 → 去重后 35 个接口** | 正确 |

第三轮的口径：

- 只收回放结论**不是"通过"**的卡片：11 不通过 + 40 待确认 + 1 未授权访问 = 52 条；
- 按端点去重后 35 个接口（1 个未授权访问 `/usercenter-api/free/ms/oauth/get-token` 高危，
  11 个越权不通过，23 个越权待确认）；
- 端点只取可见路径。卡片 `title` 属性里带着内网 IP 和端口
  （`http://10.250.4.84:38080/...`），**不能进对外交付物**——这是本轮专门守的一条线；
- 责任判定：35 个接口全部归**研发中心**（接口语义/鉴权类），工程中心 0 类；
- 建议来源全部内部（安全池历史案件 + 知识库），代码类有内部方案时按红线不搜互联网。

## 四、演练中暴露的问题（都已修）

1. **通用解析把结构当漏洞**（363 条）。根因是没有按"回放卡片 + 结论"这个结构切块，
   只按标题行找条目。→ v2.7.0 补 `_parse_xingqiu_api_security_html` 专项解析器，
   加 `tests/test_scanner_parsers.py` 用例（含"通过项不出条""title 属性里的内网 IP 不
   进端点字段"两条断言）。
2. **收紧的尺度难拿捏**。v2.6 一刀切收紧后归零，说明"判定条件"和"条目边界"是两件事：
   前者管收不收，后者管从哪里切。v2.7 把两者分开实现。
3. **内网地址泄漏风险**。卡片路径在正文里是干净的，但 `title` 属性里带 IP + 端口。
   解析器只取正文路径，并在测试里固化这条断言——对外文档出现内网地址是不可接受的。

## 六、演练中撞见的第四个问题：内部先例原文带内网地址（v2.8.0 修）

方案生成后逐字检查交付物，发现正文里有 **135 处内网 IP**（`10.255.18.31:8080`、
`10.250.4.84:38080` 等）。逐条溯源后确认不是解析器漏出去的——漏洞名称和端点字段
都是干净的路径——而是**安全池历史案件的处理记录原文**：先例的「测试验证」段落里写着
"测试版本：1.7.3.93 http://10.255.18.31:8080/bigdata-api/free/transformer/tree 已屏蔽此接口"，
这段原文作为"当时是怎么修的"被引进方案，地址跟着一起出去了。

已有的脱敏只覆盖案件描述（去 HTML、去全部 URL、过凭据红字帽），没有覆盖先例原文。
v2.8.0 补上：私网/环回/链路本地 IP（含端口）统一遮成 `[内网地址已省略]`，凭据再过
红字帽；公网地址和域名不动，所以"参考案件 #520604"这类真正有用的链接仍然保留。
用同一个 enriched.json 重生成验证：**135 处 → 0 处**，遮出 154 个占位标记，
方案正文的可读性和参考价值没有损失。

这条的价值在于：**光看漏洞字段干不干净不够，必须逐字检查最终交付物**——内网地址是
从"看起来完全无害的历史先例"里漏出去的。

## 七、演练结论

- 这个案件从"解析不出来"到"方案与现场分工逐项对应"，靠的是三次迭代，说明**解析器
  必须按真实报告结构逐个攻，不能指望通用解析兜底**。
- 案件本身的处理已经走完（研发改码 → 人工审核 → 转测试），skill 输出的清单与现场
  动作一致，可以拿给测试人员赵欣做复测参考。
- 遗留：`title` 属性这类"看不见的内网地址"需要在新增解析器时逐个案检查，回归基线
  （`scripts/regression_check.py`，14 个样本组）目前不覆盖这个案件的附件，补样本要
  先做脱敏。
- 交付物层面的检查（不只是漏洞字段）要固化成习惯：本轮 135 处内网地址来自内部先例
  原文，字段级检查发现不了。
