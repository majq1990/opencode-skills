【强制】禁止使用select *

数据传输过多增加额外开销

目前公司产品统一使用自定义函数库抹平不同数据库的函数差异，在代码提交时存在检测并阻断
低代码体系下，后续也会拦截含有不兼容函数的sql
请至钉钉文档查看附件《数据库差异对比及事项安排》。

【强制】减少or条件的使用
反例：行政区划树，需要在前端明确是city_id还是street_id传给后台，不能组合为多个or条件
【强制】or 转换为 in
in查询会走二分查找，时间复杂度会降低至O(log n)，or查询的时间复杂度为O(n)
在列表值较少时，or =和in的效率差不多，列表值超过10个时，in效率更高
not in 与and也有类似效果，列表值多时，推荐not in而非 and <>
反例：超过10个的or条件
正例：优先使用in，在比较值10个以上时，时间节省大约1倍

【推荐】视图中使用外置变量
灵珑的视图生成的SQL默认按通用的规则自动化处理，生成的SQL的性能存在局限性。可以使用视图模板语法和视图变量来控制sql的输出，从而达到优化的效果。
外置变量
一般由会作为用户条件输入传入，在视图收到之后通过SQL模板技术对该变量进行特殊条件处理，以便对生成sql条件进行控制。
如何定义变量
${变量名}  ： 自动解析出变量名，默认等值操作符
${变量名__操作符__value} ：带操作符的变量名
操作符：主要用于列表自动生成的查询字段默认的操作符类型。
比如
创建的列表使用动态参数作为查询条件时，操作符就固定且不能更改

【推荐】视图中使用内置变量
灵珑 SQL视图之前只有外置变量，主要由外部传入值来控制sql生成，通过这种机制可达到优化性能的目的。但是存在一个场景存在两种不同模式，要求不同模式下生成sql规则不同，如列表记数。于是引入内置变量来解决此类问题
内置变量
这些变量是平台内部定义，不需要外部传入。在sql设计阶段可以限制这些变量值来控制sql的生成。
使用说明
sql_mode_/sql_fields_
使用场景
sql_mode_
主要用于列表查询与计数场景区分，以便基于内置的sql_mode_来针对数据查询和计算进行差异化配置
查询分页数据的接口，内部逻辑会设置 sql_mode_ = 'query'
查询分页数据的接口，内部逻辑会设置 sql_mode_ = 'count'
sql_fields_
主要与sql_mode_配合对计数sql中不必要列进行输出控制，如：
列表查询时没有传条件时，就不输出列
判断依据：sql_fields_.size() == 0

【推荐】列表计算字段批量计算
杭州项目中有部分箱子是通过计算字段来获取部门处理意见，计算字段又是通过api从两张大表查询该数据。一个列表查询20条数据，就会触发20个内部请求，从而引发请求阻塞等问题
解决方案
计算增加是否批量执行配置，后端解析到该配置之后，参照导航属性的实现方案，将当前页面数据通过约定的变量#{parentList_}传递给api，然后就可以在api上读取相关数据完成二次查询逻辑。
列表配置
列表中存在使用 API_CALL 公式的计算字段，为避免每一行数据都调用一次 API_CALL 公式，需开启批量执行开关。

【推荐】COUNT性能优化
COUNT_OPTIMIZE
在灵珑平台中，当通过视图创建列表并执行数据查询时，系统会自动调用 count 接口对结果集进行总数统计。默认情况下，该统计 SQL 的生成方式如下：
SELECT COUNT(0)
FROM (
    -- 视图原始SQL
    SELECT ...
    FROM table
    WHERE ...
) WHERE -- 列表筛选条件
此方式将视图 SQL 作为子查询嵌套，外层再拼接列表的过滤条件进行计数。在数据量较大或视图复杂时，性能较差。
为提升性能，平台支持 “计数优化” 功能。开启后，系统会尝试将视图 SQL 与列表筛选条件合并，直接在基础表上执行计数操作，生成如下形式的 SQL：
SELECT COUNT(1)
FROM table
WHERE -- 视图中的 WHERE 条件
  AND -- 列表中的筛选条件
这种方式避免了子查询嵌套，可以显著提高计数效率。
启用方式
在视图 SQL 中未配置独立的计数 SQL；
在视图 SQL 的开头或合适位置添加注释标记：
/** COUNT_OPTIMIZE */
注意：注释必须为 /** COUNT_OPTIMIZE */ 格式，大小写敏感，不可有空格错误。
不支持的场景
以下情况不支持启用计数优化，否则可能导致解析失败或结果异常：
其他注意事项
CASE WHEN 表达式必须完整
所有 CASE WHEN ... THEN ... ELSE ... END 必须完整书写，禁止省略  END：
-- 正确
CASE WHEN a > 1 THEN 'A' ELSE 'B' END

-- 错误（缺少 END）
CASE WHEN a > 1 THEN 'A'
首次查询较慢，后续走缓存
启用优化后，第一次查询会触发 SQL 的结构化解析，并缓存解析结果；后续相同视图的查询将直接使用缓存，性能大幅提升。
建议启用后验证接口返回
优化后应手动测试列表接口是否正常返回数据和总数，确保无语法错误或逻辑偏差。

COUNT_CACHE
在大量列表计数查询比较耗时的环境下，即使使用了各种优化手段。但是高并发场景下依然存在性能问题。比如福建12345早晚高峰期时段容易出现服务宕机问题。
可以在视图上需要增加计数缓层配置
格式：
/** COUNT_CACHE(timeout，expr) */
参数说明
timeout: 缓存时间，单位毫秒。即缓存时间内同样的sql和参数，直接从缓存取计数值，不查询数据库
expr: 条件表单时，可以是常量true，也可以使用内置变量表达式
示例1：/** COUNT_CACHE(30000，true) */
示例2：/** COUNT_CACHE(30000，${query_fields_.size()>0}) */
使用说明
/** COUNT_CACHE(timeout,expr) */  可以与  /** COUNT_OPTIMIZE */  配合使用
此配置仅影响部件数据计数（视图计数不受影响）
