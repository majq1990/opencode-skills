## §1 数据模型配置（3分）

### 1.1 新建数据视图（数据模型）

1. 在应用左侧菜单进入**数据视图 / 数据模型**管理入口（菜单名可能叫"数据视图""数据模型""数据中心"等，以现场界面为准）。
2. 点【新建】/【新增】，选择**数据视图（SQL 语法）**类型（不是业务实体）。
3. 名称填写可辨识的名字，例如：`设备巡检标签列表-主模型`。
4. **数据源选择**：下拉选择本题业务库数据源（即 §0.2 问清的那个库，含 `iot_inspection_task` 表的库）。选错库 SQL 一运行就报表不存在。

### 1.2 粘贴主 SQL

把下面整段 SQL 原样粘贴进 SQL 编辑框（这段就是 3 分的主体，一个字符别改）：

```sql
SELECT
    t.task_id,
    t.task_code,
    t.device_code,
    t.device_name,
    t.device_type_name,
    t.site_name,
    t.area_name,
    t.inspect_org_name,
    t.inspector_name,
    t.task_status_name,
    t.risk_level_name,
    t.plan_start_time,
    t.plan_end_time,
    t.finish_time,
    t.task_desc,
    t.inspect_result,
    '' AS tag_names,
    '' AS tag_type_names,
    '' AS tag_group_names,
    '' AS tag_descs
FROM iot_inspection_task t
WHERE 1 = 1

/*计划开始时间：必填介于。#if #else 判空——不选时间不出数据*/
#if(plan_start_time_start != null && plan_start_time_start != '' && plan_start_time_end != null && plan_start_time_end != '')
    AND t.plan_start_time BETWEEN '${plan_start_time_start}' AND '${plan_start_time_end}'
#else
    AND 1 = 2
#end

/*巡检任务编号：包含（非必填）*/
#if(task_code != null && task_code != '')
    AND t.task_code LIKE '%${task_code}%'
#end

/*巡检任务状态：等于（非必填）*/
#if(task_status_name != null && task_status_name != '')
    AND t.task_status_name = '${task_status_name}'
#end

/*====== 高级检索 4 参数：exists 子查询，禁止连表，都过滤 delete_flag = 0 ======*/

/*标签名称：模糊*/
#if(tag_name != null && tag_name != '')
    AND EXISTS (SELECT 1 FROM iot_inspection_task_tag tt
        WHERE tt.task_id = t.task_id AND tt.delete_flag = 0
        AND tt.tag_name LIKE '%${tag_name}%')
#end

/*标签类型：模糊*/
#if(tag_type_name != null && tag_type_name != '')
    AND EXISTS (SELECT 1 FROM iot_inspection_task_tag tt
        WHERE tt.task_id = t.task_id AND tt.delete_flag = 0
        AND tt.tag_type_name LIKE '%${tag_type_name}%')
#end

/*标签说明：模糊*/
#if(tag_desc != null && tag_desc != '')
    AND EXISTS (SELECT 1 FROM iot_inspection_task_tag tt
        WHERE tt.task_id = t.task_id AND tt.delete_flag = 0
        AND tt.tag_desc LIKE '%${tag_desc}%')
#end

/*标签分组：精准匹配（等于）*/
#if(tag_group_name != null && tag_group_name != '')
    AND EXISTS (SELECT 1 FROM iot_inspection_task_tag tt
        WHERE tt.task_id = t.task_id AND tt.delete_flag = 0
        AND tt.tag_group_name = '${tag_group_name}')
#end

ORDER BY t.plan_start_time DESC
```

SQL 要点（写前默读一遍）：
- **`'' AS tag_names` 等 4 个占位列必须写**：主 SQL 不联查子表，但响应结构里要有这 4 个扩展字段，后置脚本才有字段可回填、API 后置转换才能解析出这些输出字段（参考《数据模型、高级检索》官方示例里 `'' as lable_topic` 的做法）。
- 时间介于参数**必须命名** `plan_start_time_start` / `plan_start_time_end`（字段名 + `_start`/`_end` 后缀），这是灵珑自动接收介于条件的命名规范，写错查询面板传不进来。
- `#else AND 1 = 2` 就是"不选时间列表数据为空"的实现，这是 1 分的评分点，不能省。
- 灵珑 SQL 模板语法：字符串变量在 SQL 中要加引号 `'${xxx}'`；数值不加。判空固定写法 `#if(x != null && x != '') ... #end`。

### 1.3 点【运行】生成参数

1. SQL 粘贴完，点编辑器上方/下方的**【运行】**按钮（《数据模型、高级检索》：写好 sql 后需要点击运行之后**右侧会自动生成参数**）。
2. 运行会提示需要参数值或直接执行：给 `plan_start_time_start` / `plan_start_time_end` 填一对覆盖考试数据的测试时间（如 `2020-01-01 00:00:00` ~ `2030-12-31 23:59:59`），其余参数留空。
3. 看下方结果区：应返回主表数据行，且每行末尾带 4 个空字符串的 `tag_names / tag_type_names / tag_group_names / tag_descs` 列。报错先修 SQL，再继续。

### 1.4 右侧参数列表逐个设置必填

运行成功后，右侧参数区应自动列出 8 个参数。**逐个核对并设置必填勾选**（《数据模型、高级检索》：根据业务逻辑调整过滤字段是否是必填）：

| 参数名 | 必填勾选 |
|--------|---------|
| plan_start_time_start | ✅ 勾上 |
| plan_start_time_end | ✅ 勾上 |
| task_code | ❌ 不勾 |
| task_status_name | ❌ 不勾 |
| tag_name | ❌ 不勾 |
| tag_type_name | ❌ 不勾 |
| tag_desc | ❌ 不勾 |
| tag_group_name | ❌ 不勾 |

- 若右侧没出全 8 个参数：多半是 SQL 里 `#if` 拼写有误（比如 `#lf`、少了 `#end`），回去核对再点【运行】。
- 必填勾选控件的具体样式（复选框/开关）以现场界面为准，但语义就是"该参数必传"。

### 1.5 打开分页开关

在数据模型属性区找到**【是否分页】**开关，置为**开**（《列表查询基于Hook查询》3.4.1：开启"是否分页"后 `pageIndex` 和 `pageSize` 才生效）。这是评分点"打开分页开关（1分内含）"，也是后面列表分页的前提。开关具体位置在 SQL 编辑器旁属性面板（以现场界面为准）。

### 1.6 保存并登记 ID（登记表 A 项）

1. 点【保存】。
2. **复制数据模型的接口地址 / 模型 ID**：
   - 方式一：界面上若有"复制接口地址/接口ID"按钮，直接复制；
   - 方式二（《数据视图（sql语法）》明确写过）：**数据模型 id 获取方法——浏览器地址栏最后的一串 id**（UUID）。
3. 记入登记表 **A** 项。§3 配 API 地址、或直接拼查询相对路径时要用。

### ✅ 本步验证
- [ ] 点【运行】给必填时间传值 → 有数据返回，行尾带 4 个空占位列
- [ ] 把时间参数清空再运行 → **0 行**（`#else AND 1=2` 生效）
- [ ] 右侧参数列表 8 个参数齐全，两个时间参数已勾必填
- [ ] 【是否分页】= 开，已保存，模型 ID 已登记

### ⚠️ 注意事项
- **红线**：主 SQL 里出现 `JOIN iot_inspection_task_tag` 即违反约束（禁止大表联查），高级检索也只能 exists 不许连表。
- 别顺手把 `ORDER BY` 删了或换字段；也别把 4 个占位列改成别的名字——占位列名必须与 §4 后置脚本回填字段、§5 骨架视图列名**三处完全一致**。
- 数据源选错库，后面 API 一路 500，回头先查这里。

## §2 全局变量配置（1分）

后置脚本里的数据库（数据源）名称**不允许写死**，必须走全局变量（静态变量）。

### 2.1 进入系统变量管理

1. 在应用管理/应用设置里找到**【系统变量】（变量管理）**入口（《V1.6.0.0应用全局变量管理》：变量管理分为会话变量管理和静态变量管理；入口具体位置以现场界面为准）。
2. 切换到**【静态变量】**标签页（不是会话变量——会话变量是表达式，静态变量才是常量）。

### 2.2 新增静态变量（逐项填写）

点【新增】，弹出新增静态变量窗口，逐项填：

| 属性 | 填什么 | 限制（官方文档） |
|------|--------|------|
| 名称 | `数据源名称` | 最多 30 个字符；同一应用内会话变量与静态变量不允许重名 |
| 常量值 | 当场业务库的库名，如 `iot_business`（登记表 D 项） | 最多 100 个字符 |

填完点【确定/保存】。

### 2.3 复制变量 ID（登记表 B 项）

1. 保存后回到静态变量列表，找到刚建的"数据源名称"这一行。
2. **复制其 ID**：形如 `bd_var:4ea81933-13ff-4d82-af96-b110b4a2f82c`。
   - V1.6.0.8 及以上版本，列表里的 ID 自带 `bd_var:` 前缀，直接整串复制；
   - 旧版本 ID 无前缀，引用时要自己写成 `bd_var@{变量id}` 的形式（官方兼容写法）。
3. 记入登记表 **B** 项。

### 2.4 脚本中的三种取值写法（§4 要用，先备着）

```groovy
// 方法一（通用，推荐）：AppConstUtils 直接取静态变量值
var dbName = com.egova.lowcode.data.util.AppConstUtils.getValue("bd_var:你的变量ID");

// 方法二（1.5.3.88 / 1.6.0.26 及以上，来自《API管理》4.6）：
var dbName = variables['STATIC_ENV']['数据源名称'];

// 方法三（1.5.3.88 / 1.6.0.26 及以上，静态变量名称优先级高于环境变量名称）：
var dbName = apiEnvUtil.getApiEnvInfo('数据源名称');
```

> 160 以上版本官方建议用全局变量替代老写法 `variables['env'].dealDbName`（《数据模型、高级检索》原文）。

### ✅ 本步验证
- [ ] 静态变量列表里能看到"数据源名称"，常量值 = 当场库名
- [ ] ID 已复制到登记表 B（确认是否带 `bd_var:` 前缀，对应版本写法）

### ⚠️ 注意事项
- 库名值抄准，多一个空格后置脚本 `sql.ofNamed()` 就找不到数据源。
- 官方文档提示：**API 前置和后置脚本引用的变量不随应用导出**——考试不涉及迁移可忽略，但别指望换环境自动带过去。
- 别建成会话变量；会话变量是表达式求值，评分点要的是"静态变量存数据源名称"。

## §3 API 配置（3分）

进入应用**【API管理】**（以下界面流程全部来自官方《API管理》文档，可放心照做）。

### 3.1 新增分组 + 新增接口

1. **新增分组**：点 API 列表后面的按钮（＋/新增分组），新建分组，名称如 `设备巡检`。
2. **新增接口**：点分组后的 **【...】** → 点【新增接口】→ 弹窗中：
   - 接口名称：`设备巡检标签列表查询`
   - 接口位置分组：选刚建的 `设备巡检`
   - 接口类型：**GET**（下拉四选一：GET/POST/PUT/DELETE，本题必须 GET——GET 请求分页参数平台自动附带，不需要手工处理）
   - 点【确定】，接口出现在分组下。
3. 左侧列表**选中该接口**，右侧出现接口属性设置窗口，后续所有配置都在这里做。

### 3.2 环境变量 + 接口地址

**不要把 ip:端口写死在地址栏**，用环境变量（《API管理》第3节：便于使用变量方式配置 ip 和端口号，减少重复配置；环境变量按应用隔离）。

1. 点 API 管理界面的**【环境变量】**按钮 → 【新增】→ 填：
   - 变量名称：如 `本环境服务地址`
   - 变量值：本环境服务的 `http://ip:端口`（现场提供/从数据模型接口地址里截取）
   - 保存。
2. 回到接口配置：接口地址一栏**下拉选择该环境变量**，后面的输入框填**相对路径**——即数据模型的查询相对路径（用登记表 A 项的接口地址去掉 ip:端口部分；具体地址格式照当场提供的为准）。
3. 支持 http 和 https；右侧也可以直接输入完整地址，但本题评分要求用环境变量方式。
4. **点【保存】**（官方原文：建议实时点击【保存】）。

### 3.3 授权认证 + 授权管理（1分相关）

没配授权接口 401，"授权配置正确"占 1 分的一半，另一半是地址正确。

1. 点 API 管理界面的**【授权认证】**按钮 → 【新增】授权：
   - 授权类型四选一：**脚本（默认选中）**、Api Key、Base Auth、OAuth2；
   - 按当场环境要求配置（通常选**脚本**或直接复用平台已有的授权条目——考场一般已备好，能复用就复用，别自己现写认证脚本）。
   - 保存。
2. 回到接口配置 → 切到**【授权管理】**标签页 → 在下拉/列表中**选中刚才那条授权**。
3. 点【保存】。

### 3.4 参数 Tab：逐个新增 8 个 Query 参数（1分）

切到接口的**【参数】**标签页。官方界面行为：Query 默认收缩，**单击展开**；点【新增参数】填"参数名、参数值、备注"；新增参数默认勾选状态，**勾选上才生效**；右侧操作列可删除/上移/下移/置顶/置底。

逐个点【新增参数】，按下表录 8 行（参数值填测试值或留空，备注照抄说明列）：

| # | 参数名 | 参数值（测试用） | 备注/说明 | 必填 |

### 4.2 粘贴 groovy 脚本并替换变量 ID

把下面整段粘贴进后置脚本编辑框，然后**只改一处**：把 `bd_var:你的变量ID` 换成登记表 **B** 项的完整 ID：

```groovy
import java.util.stream.Collectors;

// 1. 反序列化数据模型返回结果
var dataMap = com.egova.json.utils.JsonUtils.deserialize(data, Map.class);

// 2. 收集本页主表返回的 task_id 集合
var taskIds = null;
if (dataMap && dataMap.result && dataMap.result.size() > 0) {
    taskIds = dataMap.result.collect { it.task_id };
}
if (!taskIds) {
    return
}

// 3. 数据源名称：必须通过全局变量获取，禁止写死库名（1分评分点）
var dbName = com.egova.lowcode.data.util.AppConstUtils.getValue("bd_var:你的变量ID");
var queryTemplate = sql.ofNamed(dbName);

// 4. 按 task_id 批量 in 查询子表，过滤 delete_flag = 0（评分点）
var tagList = queryTemplate.forList(
    'select task_id as taskId, tag_name as tagName, tag_type_name as tagTypeName, ' +
    'tag_group_name as tagGroupName, tag_desc as tagDesc ' +
    'from iot_inspection_task_tag ' +
    'where delete_flag = 0 and task_id in (:taskIds)',
    5000, ['taskIds': taskIds]);

// 5. 按 task_id 分组，逗号拼接四类标签信息
var nameMap  = new HashMap();
var typeMap  = new HashMap();
var groupMap = new HashMap();
var descMap  = new HashMap();
def appendVal = { map, key, val ->
    if (val == null || val == '') { return }
    var old = map.get(key);
    map.put(key, old == null ? val : old + '，' + val);
}
for (tag in tagList) {
    appendVal(nameMap,  tag.taskId, tag.tagName);
    appendVal(typeMap,  tag.taskId, tag.tagTypeName);
    appendVal(groupMap, tag.taskId, tag.tagGroupName);
    appendVal(descMap,  tag.taskId, tag.tagDesc);
}

// 6. 回填每行扩展字段（字段名与主 SQL 占位列一致）
for (var i = 0; i < dataMap.result.size(); i++) {
    var row = dataMap.result[i];
    row.tag_names       = nameMap.get(row.task_id);
    row.tag_type_names  = typeMap.get(row.task_id);
    row.tag_group_names = groupMap.get(row.task_id);
    row.tag_descs       = descMap.get(row.task_id);
}

// 7. 序列化返回
return com.egova.json.utils.JsonUtils.serialize(dataMap);
```

3. 若现场是旧版本（ID 无 `bd_var:` 前缀），按 §2.3 的兼容写法处理；或改用 §2.4 的方法二/方法三按名称取值。

```js
function main(pageId, param) {
    // 纪律：不要修改 param（尤其 param.paging）——分页参数由平台经
    // param.paging.pageIndex / pageSize 自动携带，导出功能复用同一 param，
    // 改了会导致导出数据与查询结果不一致（官方明文，见 list-scripts-guide 分页规范）
    return new Promise((resolve, reject) => {
        console.log(pageId, param);
        // ↓↓ 改成你自己的 API 接口 ID（登记表 C）↓↓
        const apiId = "27b84536-aea0-48df-b9ee-90ff69613c26";
        // 新版入口 DATA_EXECUTOR()；旧版平台为 api.API_DATA_EXECUTE(...)，1.4.4+ 两者兼容
        api.DATA_EXECUTOR().executeApiModelForList(apiId, "BUNCHES", param, { lostAbility: "01" })
            .then(res => {
                resolve(res);
            }).catch(err => {
                console.error("[hook] executeApiModelForList 调用失败:", err); // 排错抓手，保留
                reject(err);
            })
    })
}
```

脚本要点：
- `"BUNCHES"` = 灵珑 API（`WIDZOM` 是智云，别选错）。
- `lostAbility: "01"`：第一位 0 = 有分页能力（数据模型已开分页），第二位 1 = 缺失排序能力（这种模型代理列表不支持点表头排序）。

- `.catch` 里保留 `console.error` 打印错误对象并 `reject(err)`，预览 F12 Console 可直接看到失败原因（脚本规范：Promise 必须有 `.catch()`）。
- 本脚本未用到 `this`；若自行扩展 hook 逻辑要用 `this`，按脚本规范在函数首行加 `const self = this;` 后统一用 `self`（function 回调里 `this` 指向会变）。

2. 绑定字段：选骨架视图里的 **`plan_start_time`**（原字段名，未起别名）。
3. 匹配符：**介于**。
4. 校验设为**必填**；可给默认值（如最近一个月）方便演示。
5. 标题改中文"计划开始时间"。

**条件 2：巡检任务编号（非必填，包含）**
1. 控件类型：**单行文本**。
2. 绑定字段：**`task_code`**。
3. 匹配符：**包含**。
4. 非必填。标题"巡检任务编号"。

**条件 3：巡检任务状态（非必填，等于）**
1. 控件类型：**单行文本**（或下拉单选，若现场给了状态字典）。
2. 绑定字段：**`task_status_name`**。
3. 匹配符：**等于**。
4. 非必填。标题"巡检任务状态"。

配完保存部件/页面。

### 6.2 原理说明（理解了才不慌）

- 时间字段介于查询会自动按 `plan_start_time_start` / `plan_start_time_end` 传参（《列表查询基于Hook查询》：对于介于条件的约定在列名前加 start、end 前缀）——正好命中数据模型参数名。
- hook 列表的查询面板匹配符实际**不生效**，真正过滤逻辑在数据模型 SQL 里；但官方要求匹配符**仍要配成与 SQL 一致**（时间=介于、编号=包含、状态=等于），"避免产生误解"——这也是"查询控件配置正确"3 分的采分细节。

- [ ] F12 看请求 param.condition：三个条件的值都传进去了

## §7 高级检索配置（4分）

前提：灵珑版本 > 1.5.3.40。以下步骤即官方《高级搜索》3.1 配置步骤的展开。

### 7.1 新增"高级搜索"顶部操作按钮

1. 在**列表或页面**配置上 → **新增顶部操作** → 选择/添加**"高级搜索"按钮**。
2. 点该按钮的**编辑**按钮，可调整按钮常规属性（名称、图标等，默认即可）。

### 7.2 打开设计组件界面

点按钮的**【设计组件】**，打开高级搜索的配置页面——**实际为复用表单配置页面**（官方原文），所以操作手感和配表单一样：左侧组件库拖组件、右侧配属性。

### 7.3 拖拽 4 个标签字段组件并绑定

逐个从组件库**拖拽**组件到画布，然后选中组件**绑定字段、设置默认匹配规则**（官方步骤4）：

| 顺序 | 组件 | 绑定字段（=参数名） | 匹配符 | 标题 |
|------|------|--------------------|--------|------|
| 1 | 单行文本 | tag_name | 包含/模糊 | 标签名称 |
| 2 | 单行文本 | tag_type_name | 包含/模糊 | 标签类型 |
| 3 | 单行文本（或多行输入） | tag_desc | 包含/模糊 | 标签说明 |
| 4 | 单行文本（或下拉单选） | tag_group_name | 等于 | 标签分组（精准匹配） |

- 绑定字段就是 §5.1 骨架视图末尾那 4 个单数占位列，也正好等于数据模型/ API 的参数名。
- 官方支持的组件清单里包含：单行文本、多行输入、下拉单选、日期范围选择等，都支持显示匹配符。
- **开放设置**：开启则最终用户可在高级搜索页面上切换匹配符——本题匹配符要求固定，**不开**为稳。
- 标题宽度不齐可按官方 3.3：选中组件 → 点页面 → 调整标题宽度。

### 7.4 隐藏必填时间字段的处理

数据模型的 `plan_start_time_start/end` 是必填参数，高级检索触发查询时也必须带上时间，否则命中 `#else AND 1=2` 全空。题目原文："时间字段必填不展示即可"。

1. 再拖一个**日期范围选择**组件（官方 3.2：要配介于条件必须用日期范围选择，且它的匹配符只支持介于，不能切换）。
2. 绑定字段：**`plan_start_time`**，匹配符固定为介于。
3. 设为**必填**，并**给默认值**：一个覆盖考试数据的大范围（如 2020-01-01 ~ 2030-12-31）。
   - 官方 3.2 注意：早期版本传入时分秒为 00:00:00~次日00:00:00；灵珑 1.5.3.61、1.6.0.13 及以后支持 00:00:00~23:59:59。默认值范围放大一点可规避边界。
4. 把该组件设置为**隐藏**（组件显隐属性关闭/hidden；显隐属性的具体名称位置以现场界面为准）。这样用户只看到 4 个标签字段，但查询参数完整。
5. **兜底方案**：若当场版本隐藏后不传值（预览实测），则退而求其次——不把时间放进高级搜索，靠普通查询面板的必填时间与高级检索条件**合并生效**（hook 的 param.condition 会同时携带两者）。F12 看 console.log 打印的 param，实测哪种能把时间带上就用哪种。

### 7.5 保存与预览

1. 官方步骤5：组件支持定义默认值，**但查询面板不会自动查询，需手动点【查询】**——演示时记得先点查询。
2. 配置完成点**【保存并退出】** → 退回到页面/部件设计器 → 再点**【保存】** → 预览查看效果（官方步骤6，两层保存都要点）。

### 7.6 匹配符与真实逻辑的关系

官方《高级搜索》注意事项："如果是列表走 hook，按照数据模型里的查询条件来，**匹配符不生效**，应该是合理的"。即 4 分的实质在 **§1.2 的 SQL** 里（3 个 `LIKE '%…%'` + 1 个 `=` + exists + delete_flag=0），这里只要**参数名绑对、值能传到 API** 就行。匹配符照表配一致，只为界面语义正确。

### ✅ 本步验证
- [ ] 预览点"高级搜索"按钮 → 弹出面板只显示 4 个标签字段（时间字段隐藏）
- [ ] 输 tag_name 关键字点查询 → 列表被过滤；其余 3 个字段同样逐个试
- [ ] F12 看 param：高级检索的值 + 时间参数都在 condition 里
- [ ] 打开面板再次进入时上次条件保留（官方 3.4 行为，属正常，不是 bug）

### ⚠️ 注意事项
- 官方提示：**目前不支持查询面板和高级查询同时使用（会存在一些问题），建议搜索框和高级搜索搭配使用**。本题两者都要，预览时重点回归"普通过滤仍生效 + 高级检索也生效"；若冲突，优先保证参数都进了 hook 的 param。
- 【重置】只清空搜索框内容，不重置匹配符；实时赋值的时间默认值下次打开不刷新（官方 3.4）——考试演示前手动确认时间值还在。
- 4 个字段一个都不能换、不能少；多拖了别的字段也删掉。

## §10 常见坑（原 14 条全保留，编号对应正文 ⚠️）

1. **介于参数命名不符**：写成 `startTime/endTime` 或 `plan_start_timeStart` 都收不到查询面板的介于值——必须是 `plan_start_time_start` / `plan_start_time_end`（字段名+后缀）。直接丢时间条件 1 分并连带"过滤生效"1 分。（§1.2）
2. **忘写 #else AND 1=2**：只判空不写 else，不选时间会查出全量数据，"不选时间列表数据为空"评分点丢 1 分。（§1.2）
3. **写死库名**：后置脚本里 `sql.ofNamed('iot_business')` 直接写库名 = 全局变量 1 分丢掉。必须先建静态变量再用 `AppConstUtils.getValue("bd_var:…")` 取。（§2/§4）
4. **exists 忘过滤 delete_flag=0 / 后置脚本忘过滤**：两处都要有 `delete_flag = 0`，评卷会拿已删除标签数据测。（§1.2/§4.2）
5. **图省事直接 JOIN 子表**：主 SQL `LEFT JOIN iot_inspection_task_tag` 是本题**红线**，约束里明确禁止大表联查，高级检索也只能 exists 不许连表。（§1）
6. **hook 里 apiId 没改**：粘了示例脚本忘换成自己的 API 接口 ID，列表空转，hook 1 分 + 展示 2 分连带丢。同时确认类型是 `"BUNCHES"` 不是 `"WIDZOM"`。（§5.3）
7. **主 SQL 没写 `'' AS tag_names` 占位列**：后置转换解析不出扩展字段、骨架视图/列表也没这列可绑，标签列展示不出来。占位列 + 后置脚本回填字段名 + 骨架视图列名，三处必须完全一致。（§1.2/§4/§5.1）
8. **骨架视图字段起了别名**：查询面板/高级检索绑定的字段名与参数名对不上，条件传不进 API。骨架视图一律用原字段名，datetime 用 `NOW()` 占位。（§5.1）
9. **模型分页与列表分页不同步**：数据模型"是否分页"和列表部件"分页"要全开（或全关），只开一边翻页错乱。（§1.5/§5.4）
10. **多配了过滤条件**：查询面板加了设备名称/设备类型/区域/风险等级等字段——题目限制死只许 3 个固定条件，多配扣分。（§6）
11. **高级检索时间没带上**：高级检索查询若不携带必填时间参数，会命中 `1=2` 全空，看起来像"高级检索坏了"。按 §7.4 处理（隐藏必填时间组件给默认值，或与普通面板时间合并生效）。（§7.4）
12. **状态字段配成包含**：`task_status_name` 必须是等于（SQL 里 `=`），配成 LIKE 精准匹配评分点不过。（§1.2/§6.1）
13. **API 改完没点保存就发送**：API 配置每步要实时【保存】，否则发送用的还是旧配置，排查半天白排。（§3 全程）
14. **groovy 脚本引号**：`forList` 的 SQL 字符串里用单引号包裹，命名参数 `(:taskIds)` 用 map 传参，别手拼 in 字符串（有注入和格式风险）。（§4.2）

## 脚本规范升级说明（2026-07-10）

本手册 JS 层已按 `references/scripting/list-scripts-guide.md`（Hook 分页规范）与 SKILL.md「② JS 脚本规范」核对升级。实际变更如下：

1. **§5.3 hook 脚本 `.catch` 增加 `console.error`**：原为空 `catch(() => reject())`，现改为 `catch(err => { console.error(...); reject(err); })`，预览 F12 可直接看到失败原因（规范第 5 条：Promise 必须有 `.catch()` 且要有错误处理）。§8 复查清单同步注明该打印属规范保留项，不算调试残留。
2. **§5.3 脚本内新增 param 纪律注释**：函数首部注释明确"不要修改 param（尤其 `param.paging`）"，并在脚本要点补充分页链路说明——`param.paging.pageIndex/pageSize` 平台自动携带透传、接口必须返回总数（`totalCount`）分页才生效（对照 list-scripts-guide「hook 查询分页处理」）。
3. **§5.4 新增分页链路回顾一条**：翻页 → param.paging → hook 透传 → GET 自动带参 → totalCount → 渲染页码，任一环手工改动即翻页错乱。
4. **`const self = this;` 纪律**：本题 hook 脚本未用到 `this`，无需实际加行；脚本要点已补说明——自行扩展 hook 逻辑用到 `this` 时须在函数首行加 `const self = this;` 统一用 `self`。
5. **API 入口无需迁移**：本手册 hook 已是新版 `api.DATA_EXECUTOR().executeApiModelForList(apiId, "BUNCHES", param, { lostAbility: "01" })` 入口，保持不动；脚本内及要点均注明旧版兼容写法 `api.API_DATA_EXECUTE(...)`（1.4.4+ 两者兼容，旧环境不必强改）。
6. **不适用范围**：§4 groovy 后置脚本为服务端脚本，不适用前端 JS 脚本规范，原样保留；SQL、API 配置、全局变量、高级检索操作步骤、评分表、§10 常见坑均未改动。
